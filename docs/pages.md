# Страницы (`pages/`) — подробно

Перенесено из AGENTS.md 21.10.2026 дословно, раздел «Страницы (`pages/`)» (решение владельца: в AGENTS.md — правила и ссылки). Ссылки поправлены под папку `docs/`; содержание не менялось.


Регистрируются в [app.py](../app.py) через `st.navigation`, два раздела:
«Работа» (guide, dashboard, catalog, synthesis, photo, content, textgen) и «Управление»
(matrix_setup, methodology, settings).

### `guide.py` — «Как это работает»
Статичная инструкция для команды: 6 шагов + анимированная схема потока
матрица → сбор → диагноз → синтез → Amazon. Живой статус на схеме
(свежесть сбора, число болей).
Читает: `listing_snapshots`, `diagnosis`.

### `dashboard.py` — «Диагноз» (страница по умолчанию)
Главный экран: сколько товаров требует внимания, деньги под риском, дельта
болей с прошлого прогона. Шапка и выгрузка «Исправить все → CSV · N»
считаются ПО ФИЛЬТРАМ (правило 8): под ES — «2 товаров требуют
внимания · фильтр: ES», в файле ровно боли списка. Дельта с прошлого
прогона и «✓ N здоровых» — итоги по всей базе, под фильтром скрыты.
**Боли Amazon Issues собираются с кешем** (`build_pains_cached(lang)`,
TTL как у загрузчиков Issues, язык в ключе — тексты болей переводятся).
Без кеша сборка шла на каждом клике по фильтру: на объёмах 26.09
(8065 открытых болей, 1025 строк Issues) — 0,64 с из 0,86 с скрипта,
на Cloud это и были «3–5 секунд с блёклыми цифрами». После — смена
рынка 0,16–0,23 с локально вместо 0,80–0,84. Фильтры по severity / группе правила / маркетплейсу /
поиску, два вида (карточки и таблица), пагинация по 25. Внизу — счётчик
здоровых и несобранных. Показывает только проблемные товары.
Деньги под риском = выручка ASIN × коэффициент правила (`RULE_RISK`); по товару
берётся максимум, а не сумма — проблемы пересекаются.
Читает: `diagnosis`, `listing_snapshots`, `product_matrix`, `asin_economics`
(через `services.economics`), `app_settings` (через `services.settings`).

### `catalog.py` — «Каталог»

**Возраст данных считается ПО ПРАВИЛАМ сбора, а не по календарю.**
Сбор делает job Databricks «Listing Suite Auto Collector»
(`89677076782805`, 13:00 Kyiv, время из `collection_schedule`;
ноутбук в воркспейсе владельца). Его правило, проверенное по коду
17.09: пары с заказами за 30 дней (`product_matrix.collection_tier =
'daily'`) собираются каждый прогон; остальные — `weekly`, в день,
закреплённый хэшем `MOD(ABS(HASHTEXT(asin || marketplace)), 7)`
(`weekly_day`, 0 = понедельник); `status = 'wound_down'` не
собирается вовсе. Ни `LIMIT`, ни бюджета запросов нет. Раньше
экран этих колонок не знал и показывал свёрнутый товар как отставший
на три недели, а новую пару, ждущую свой четверг, — как «не
собиралась». История: «33 выпавших» оказались `wound_down` (ставится
руками по списку `wound_down_candidates` из «Kabinet — FBA Ledger
Detail Loader»), «20 никогда» — новые пары, дождавшиеся своего дня.

На экране: свёрнутый — словом («свёрнут — не собирается · последний
сбор 26.08»), без возраста и вне «отстают»; активный — дата, возраст
словами и график («обновляется ежедневно» / «по четвергам»); новый —
«первый сбор в четверг». Отстаёт — от СВОЕГО графика: ежедневная
старше двух дней, недельная старше семи (`STALE_AFTER`). Полоса над
списком считает отстающих, ждущих первого сбора и свёрнутых по
каждому рынку. `weekly_day` берётся из базы, а для пары, которую job
ещё не размечал, считается тем же хэшем в запросе — совпадает с тем,
что назначит job.

**Рынок на Каталоге выбирается ОДИН раз — галочками, и по ним идут
список, выгрузка и сбор (26.09).** До этого переключателей было два:
галочки резали сбор и файл, выпадашка «Все рынки» ниже — список.
Коллега отметил ES и увидел на экране Италию: «показывает Италию,
когда я отсортировал по Испании». Прежние заплатки — ссылка «показать
эти рынки в списке», выгрузка по галочкам мимо списка — лечили
последствия двух переключателей; убран второй, вместе с ними.
Без галочек в списке все рынки, как раньше.

**Сбор по выбранным рынкам — тот же job, из приложения.** Подпись
«Рынки — по ним список, выгрузка и сбор», галочки рынков, кнопка
«Собрать выбранные» и рядом — что уйдёт: «ES, DE · 566 товаров
(ES 295, DE 271)» — `run_now` job'а `89677076782805` с
`notebook_params` `marketplaces` и `force=1` (`services/collector.py`).
Число названо «к сбору», и рядом — свёрнутые: «ES · 301 к сбору ·
9 свёрнутых не собираются». Список и выгрузка показывают ВСЕ пары
рынка (310), и голое «301 товар» рядом с «CSV · 310» читалось как
ошибка счёта. Счётчик над списком тоже складывается целиком: «260
товаров · с проблемами 258 · здоровых 1 · ещё не собраны 1» — раньше
было «здоровых 1», а «только с проблемами» убирало две строки, и
вторая (несобранная) нигде не называлась.
Рядом с числом — дата последнего снапшота рынка («последний сбор
17.09 10:00», при нескольких рынках — по каждому в скобках): нажимая
«собрать», надо видеть, когда собирали в прошлый раз. В табличном
виде та же дата — колонкой «Собрано».
Число стоит РЯДОМ с галочками, а не в кнопке: ряд кодов без подписи
читался как список непонятно зачем, а кнопка бывает неактивна
(идёт утренний прогон) — знать объём нужно всё равно. Три правила:
не поверх идущего run'а (`max_concurrent_runs = 1`, второй встал
бы в очередь молча — кнопка неактивна, пока run идёт, в том числе
утренний); число — только активные пары выбранных рынков,
свёрнутые не в счёт, как у самого ноутбука; ход — по базе, снапшоты
с меткой не раньше старта, фрагментом раз в десять секунд. Итог
run'а читается из `dbutils.notebook.exit`: «skipped» значит, что
ноутбук ещё не принимает параметры. Клиент Databricks — из секции
`[databricks]` секретов; принципалу нужно CAN_MANAGE_RUN на job.

Ноутбук под это ПРАВЛЕН 17.09 (бэкап рядом: «…Auto Collector BACKUP
2026-09-17»): виджеты `marketplaces`/`force`, фильтр по рынкам в трёх
выборках, и КОММИТ ПО ПАРЕ вместо одной транзакции в конце.
Доправлен 18.09 (бэкап «…BACKUP 2026-09-18b»): **ручной запуск по
рынкам берёт ВСЕ активные пары этих рынков, день недели не смотрит**;
плановый без рынков — ротация как была. До этого фильтр по рынкам
добавлялся к правилу дня: кнопка обещала «PL · 1 товар», а run
кончался «0 ok» — у единственной пары `weekly_day = 3`, а нажимали
в пятницу. Retry-выборка при ручном запуске отключена — все weekly
уже взяты. Последнее
важнее кнопки: «hot-first» в ноутбуке обещал, что при падении
значимые товары уже собраны, а одна транзакция откатывала всё; и
`fetched_at` у всех 270 строк дня совпадал до микросекунды — это
`now()` Postgres, то есть время СТАРТА транзакции, а не сбора.
С 18.09 метки станут временем самой записи, и полоса возраста
начнёт различать пары внутри одного прогона.

Принципал приложения в Lakebase — `583bf6d1-…` (kabinet-dashboard-sp):
единственная роль с правом записи в `synthesis_changes` и
`figma_layers`. `claude-uc-ro` (`b1698364-…`) — read-only для MCP,
к кнопке отношения не имеет; CAN_MANAGE_RUN на job нужен первому.

**Выгрузка — ровно то, что на экране, в CSV и Excel.** Строится из
`rows` после всех фильтров (рынок, группа проблем, поиск, «только
проблемные»), все страницы списка, и в подписи кнопок стоит число
строк — файл «всего каталога» вместо отфильтрованного был бы тихой
подменой. Кнопки стоят В РЯДУ СО СБОРОМ, выделенные, а не под
фильтрами: два действия над каталогом в одном месте. Отмеченные
рынки режут список, и файл вместе с ним; подпись называет их:
«CSV · 1 (PL)». Ряд рисуется
раньше фильтров, а число известно после них — поэтому
`render_collect` отдаёт два `st.empty()`, и кнопки заполняются позже;
пояснение «ровно то, что на экране» — в подсказке кнопки. Два формата намеренно: CSV для скриптов, XLSX для людей —
Excel открывает CSV с кириллицей и разделителями по-своему на каждой
машине. В файле есть колонки сбора (`status`, `tier`, `weekly_day`,
`fetched_at`, `age_days`) — те же, что подписаны на карточках.
В XLSX ASIN — гиперссылка на карточку Amazon через `product_url`
(не шаблон по коду рынка: у Бельгии витрина amazon.com.be), в ячейке
остаётся сам ASIN; в CSV ссылок нет.

История есть только у снапшотов: `listing_snapshots` append-only
(цена, сток, рейтинг, отзывы на каждый сбор). `asin_economics`,
`catalog_source`, `listing_attributes` — одна строка на пару,
перезаписываются; `sqp_reports` — по неделям, но последняя дата
06.09 при недельном шаге.

**Buy Box и BSR — из сборщика колонками, экран их только читает.**
Оба лежали в `raw` с июля и не читались. `sold_by`/`merchant_id` →
`buy_box_owner` (own / amazon / other / none; none — на странице нет
предложения: 264 пары на 18.09, из них 242 в наличии по SP-API) и
`buy_box_seller`. Наш merchant id один на все рынки, имя магазина
разное — различаем по id (`services/buybox.py`, копия в ноутбуке).
BSR приходит СТРОКОЙ на языке страницы под ключом на том же языке;
разбирает `services/bsr.py` — один парсер на сборщик (копия ячейкой)
и экран, тест на все девять языков живыми строками. Две ловушки,
из-за которых покрытие было разным: ключ выбирался по первому
вхождению «best|rank|posizione» (у ES перед BSR стоит «Rango de
medición», у IT — «Composizione della batteria»), а польское
«w kategorii» в предлогах не значилось. Теперь ключ узнаётся по
началу с якорем, предлоги по факту. Парсер берёт 342 из 342 строк,
где ключ есть; но сам ключ ScrapingDog отдаёт неровно — DE 26 из 258,
IE 5 из 132, ES 209 из 295 — это ограничение сборщика, а не парсера.
Для снапшотов до 18.09 колонок нет — экран читает raw тем же кодом,
и тест требует, чтобы обе дороги давали один чип.

Правила Диагноза `buy_box_lost` НЕТ намеренно: на IE `sold_by` есть
у 1 пары из 131, на co.uk у 5 из 32 — пока не проверено глазами, рынок
это или ScrapingDog там не парсит продавца, правило дало бы 130
ложных болей. Заперто тестом: правило не должно появиться раньше
проверки.

Паспорт каждого товара: тайтл, фото, видео, A+, отзывы, рейтинг, цена, BSR,
сток, продавец, экономика, SQP-метрики, атрибуты, Amazon's Choice. Показывает ВСЕ товары,
включая здоровых и конкурентов. Здоровье считает код (`health()`), не ИИ.
BSR парсится из `raw` регулярками, потому что ключ и формат зависят от языка
страницы.
Читает: `product_matrix`, `listing_snapshots`, плюс через сервисы —
`asin_economics`, `synthesis_drafts`, `synthesis_changes`, `photo_analysis`.
Атрибуты и поисковую сводку берёт из `services.attributes` и
`services.search`.

### `synthesis.py` — «Синтез»: Split 75/125
**Закладки — по виду текста и площадке, а не по состоянию (12.10.2026).**
Сейчас одна, «Title AMZ», и в ней всё, что описано ниже. Следом встанут
Title LM, Title MM, Title Cr (Leroy Merlin, ManoMano, Carrefour), затем
описание и FAQ. Генерация картинок и видео сюда не относится — она живёт
на «Контенте». Закладки по СОСТОЯНИЮ («очередь / сгенерированные / любой
товар») внутри ленты запрещены, как и раньше: `test_feed.py` пускает
только ключи `synth.tab_title_*`, `synth.tab_description`, `synth.tab_faq`.

Словарь интерфейса: **«черновика» в UI нет**. То, что выдала модель, —
«результат», собирательно «Сгенерированные», счётно «сгенерировано: N».
Слово «черновик» читается как «набросок» и скрывает, что там готовый
результат, ждущий решения. В коде и в имени таблицы `synthesis_drafts`
оно остаётся — это внутреннее имя, а не то, что видит человек.
Разбивает длинный тайтл на `title` ≤ 75 символов и `Item Highlights` ≤ 125.
Смысл разделения: title читает человек за 1–2 фиксации взгляда, Highlights
парсит ИИ-ассистент покупателя (Rufus/COSMO).
Методология тянется из `synthesis_skill` (активная версия, правится на странице
«Методология» без коммитов). **Запасной методологии в коде нет намеренно:**
раньше при сбое чтения подставлялся зашитый текст «Бренд Dnipro-M первым» —
правило, противоположное действующей v8, — и подмена шла молча. Теперь
пустой текст или версия 0 означают «методологии нет», и генерация
не запускается вовсе. Защищённые фразы размечаются по фактам SQP
(`services.seo`), после генерации результат проверяется КОДОМ: длины,
запрещённые символы, повторы слов, наличие must-keep, отсутствие forbid.
Coverage Score (доля сохранённого поискового веса) тоже считает код, не модель.
Действия в карточке разделены на две группы с чертой между ними:
«Решение по тексту» (принять, редактировать, перегенерировать) и
«Выгрузка» (скачать flat file, отправить в Amazon) — второе с отступом,
под ним история отправок. **Основная кнопка всегда одна и показывает
следующий шаг:** не принято — «Принять», принято — «Отправить в Amazon»,
отправлено — основной нет. Наверху страницы те же выгрузка и отправка,
но по всем принятым под фильтром, и в подписи «для всех принятых · N».
Карточные кнопки до приёмки неактивны: они работают с `synthesis_changes`.

**Список один, вкладок нет.** Раньше их было три — очередь,
«Сгенерированные», любой товар, — и товар переезжал между ними после
каждого действия: сгенерировал — уехал во вторую, принял — исчез и
оттуда. Первый вопрос после приёмки был «а куда он делся». Теперь
строка остаётся на месте, меняется только метка состояния: «Без
результата» → «Сгенерировано» → «Принят» → «Отправлено».

Над списком три фильтра состояния с живыми счётчиками (считают по
текущей выборке, а не по базе): «Требуют замены», «Все» (весь каталог)
и «Отправленные» (есть удачная запись в `listing_push_log`).
**«Требуют замены» — это НЕ просто правило `title_over_limit`:** диагноз
пишется сбором и живёт до следующего, поэтому товар с уже отправленным
укладывающимся тайтлом висел в списке как несделанная работа. Удачная
отправка снимает признак сразу, не дожидаясь сбора. Фильтр
по стране и поиск работают поверх. Внутри «Требуют замены» порядок
блоками: ждут решения → решение принято → без результата, между ними
разделители с числами. Блок принятого отдельный намеренно: держать
принятое под подписью «ждут решения» — то самое враньё, ради которого
вкладки и убирали.

Строка компактная и самодостаточная: галочка, текст (результат, если он
есть, иначе нынешний тайтл), под ним SKU, ASIN, рынок, «было N», метки
«старая методология (vN)» и «нет данных поиска», справа Coverage,
состояние и длина результата. **Плашка Coverage стоит всегда**: когда
числа нет, она называет причину («не считался: нет данных поиска» или
«результат сделан до подсчёта Coverage») — пустое место на её месте
не отличало «не считался» от «сейчас появится». Карточка раскрывается под строкой и
осталась прежней. Массовые действия — одной панелью над списком, все
работают по ОТМЕЧЕННЫМ строкам текущей выборки. Отметки живут отдельным
множеством пар в `session_state`, а не в ключах галочек: галочка есть
только у отрисованной строки, поэтому «Выбрать все» физически отмечала
тридцать строк экрана при выборке в сотни. Кнопки: «Выбрать все · N»,
«Сгенерировать партию», «Принять · N» (неактивна, пока у кого-то из
выбранных нет результата), «Перегенерировать · N» с той же полосой
хода, что у партии.

Наверху — разрез по рынкам (строки складываются в итог, мелкие страны
сворачиваются в «Прочие»), в блоке результата — плашка модели, которой
он сделан, и пометка, если товар уже принимался.
Читает: `diagnosis`, `listing_snapshots`, `product_matrix`, `synthesis_skill`,
`protected_keywords`, `synthesis_drafts`, `synthesis_coverage`,
`synthesis_changes`, `sqp_reports`, `asin_economics`.
Пишет: `synthesis_drafts`, `synthesis_coverage`, `synthesis_changes`.
Все числа блока выгрузки — из одного источника (принятые под текущим
фильтром), кнопки не исчезают при нуле, а строка состояния всегда
называет фильтр: «Германия: принято 3 · строк: 3 · файлов: 1». Раньше
подпись кнопки считала строки файла, соседняя — принятые правки, и ряд
говорил о разном.
Выгрузка для Amazon — настоящий шаблон Seller Central, см.
`services/flatfile_template.py`. Рядом — прямая отправка по SP-API
(`services/spapi.py`): только по одному товару и только через диалог
подтверждения.

### `photo.py` — «Фото и A+»
Аудит визуала через vision-модель. Вкладка «Галерея» — главное фото + галерея
(методология `photo_brief`), вкладка «A+ контент» — модули A+ (методология
`aplus`). Грейд считает КОД, ИИ отвечает только по чек-пунктам (true/false)
и даёт покадровый разбор + ТЗ дизайнеру. Отдельно проверяется соответствие
языка изображений языку маркетплейса.
Аудирует СНАПШОТЫ, поэтому пары без единого снапшота в списке быть
не может — но она называется под списком теми же фильтрами: «Ещё
не собраны, аудировать нечего: 2 (B0GZVXLK1Y · DE, B0GZVZQM42 · IT)».
Без этого Фото показывало 1067 при 1069 на Диагнозе и Матрице, и
расхождение выглядело потерей (две недельные пары, добавлены 23.09,
их день сбора ещё не наступил).
Читает: `listing_snapshots`, `product_matrix`, `synthesis_skill`,
`photo_analysis`.
Пишет: `photo_analysis` (`analysis_type` = `gallery` | `aplus`).

### `content.py` — «Контент»: перевод макетов Figma
Вкладок пока одна — «Перевод», структура заложена на несколько.
Дизайнер рисует карточку по-английски, продаётся она в четырёх странах;
экран отвечает на два вопроса — что не переведено и влезет ли перевод
в макет.

Вкладка называется «Перевод», а не «Локализация»: работа здесь именно
с текстом, а локализация подразумевает больше. Внутренние имена
остались прежними — префикс `loc.*` в словаре,
`services/localization.py`, таблицы `figma_*`: это код, а не то, что
видит человек (та же граница, что у «черновиков» и `synthesis_drafts`
на Синтезе).

**Ряды кнопок и строки перевода — флексом, с ключом через `css_key`.**
Веб-агент 26.09 при окне ~1100 px: главная кнопка теряла число
(«Перевести всё, чего нет · 33 стр…»), счётчик «15 / 17» и ↻ в строке
сжимались, ASIN в списке ложился в столбик по две буквы. Ряды
кнопок — по правилу 0 (`flex_row_css`), строка перевода — без
переноса, счётчик 72 px, ↻ 44 px. Строка товара в СПИСКЕ — тоже
(27.09, второй проход агента): на долях колонок кнопке доставалось
~100 px и «Перевести · ES» резалась до «Перевест…» — перенос ряда
тут не спасает, ряд один. Теперь кнопка по ширине подписи, карточка
забирает остаток, а чипы языков уходят второй строкой карточки,
а не сжимаются в столбик. Проверено в браузере на 1000 / 1100 /
1440 px; правило заперто в `test_localization.py`. Попутно нашлось, что CSS строк не
срабатывал НИКОГДА: ключ контейнера содержал id слоя «1021:737», а
Streamlit делает из ключа класс, заменяя «:» на «-», — не работала
и подсветка строки, которая не влезает в макет. Теперь ключи под
CSS собираются через `components/ui.py::css_key`; то же чинит
карточки Синтеза на рынке `co.uk` (точка в селекторе). Запирает
`test_silent_failures.py`.

**Колонка длины — то, ради чего страница и делается.** Испанский
и немецкий длиннее английского примерно на пятую часть, слой в макете
фиксированной ширины, и не влезший текст обнаруживается при ЭКСПОРТЕ,
когда работа уже сделана. Поэтому у каждой строки стоит «длина /
предел», строка с превышением подсвечивается целиком, а под таблицей
сказано, сколько строк править. Состояний четыре: влезает, впритык
(занято больше девяти десятых), не влезает, предел неизвестен —
последнее значит «слой ещё не прочитан из Figma», а не «места нет».

Пока Figma не подключена, экран показывает демонстрационный набор
и ОБЪЯВЛЯЕТ это плашкой: демо, неотличимое от настоящих данных, хуже
пустого экрана — по нему начнут считать объём работы.

**Слева макет, справа строки.** Без картинки перевод — это список фраз
без контекста: не видно, что одна строка — крупный заголовок на тёмном
фоне, а соседняя — мелкая подпись под ним.

**Карточка идёт СЛАЙДАМИ, а не одной таблицей.** Текст живёт
в слайдах `PT01…PT09`, а `.MAIN` — фото на белом фоне, где текста нет
вовсе. Одна таблица на 33 строки заставляла держать в голове, к какому
слайду относится строка; теперь блок на слайд: заголовок с числом
переводимых строк, слева его превью, справа его строки. Имя слайда
достаётся из `slot` (`B0G4S9SJ3M.PT01#3` → `PT01`), а узлы всех
слайдов по языкам лежат в `lang_nodes`. Модули A+ — те же блоки,
ПОСЛЕ слайдов (`slide_order`: фото, слайды, A+ десктоп, A+ мобайл),
с заголовком «A+ десктоп 5 · carousel 3.1»: позиционное имя `A+d05`
дизайнеру ничего не говорит, настоящее имя модуля — говорит.
Вариант d/m в имени значим, поэтому `norm_part` не переводит его
в верхний регистр.

Цена решения — запросы: девять слайдов вместо одного превью, то есть
до девяти обращений к Figma на товар и язык. Кэш суточный и по узлу,
поэтому платится это один раз в сутки.

**Макет показывается НА ЯЗЫКЕ, если он есть.** Часть товаров дизайнер
перевёл прямо в Figma, и там лежит готовая карточка с переведённым
текстом на картинке; узлы всех слайдов по языкам хранятся в
`figma_products.lang_nodes` (jsonb): `{"en": {"MAIN": …, "PT01": …}}`. Английский остаётся запасным —
языковых макетов одиннадцать на двадцать один товар, — но подпись
обязана сказать, ЧТО на экране: «макет DE, уже переведён» и «макета DE
ещё нет, показан английский» выглядят одинаково, а значат разное.

**В списке — миниатюра, ОДНА на товар.** По названию товары
не различаются: «Blower DCB-201BC» и «Blower DVB-200» читаются
одинаково.

**Миниатюра в списке — главное фото Amazon, а не рендер Figma (27.09).**
Фрейм `.MAIN` в макете и ЕСТЬ главное фото листинга — фото на белом
фоне, текста в нём нет, — а его ссылка уже лежит в последнем удачном
снапшоте (`raw.main_image`, запасной — первая из `raw.images`).
Отдаёт `amazon_photos()` одним запросом к базе на весь список;
картинку браузер берёт с m.media-amazon.com. Квоты Figma это не
тратит вовсе: на месте View (6 запросов в месяц) рендер 21 миниатюры
съедал бы запрос из шести на то, что уже есть в базе, а после 429
список стоял пустым. Проверено 27.09: фото есть у всех четырёх
товаров пробного набора. Товар без снапшота берёт СОХРАНЁННЫЙ
рендер `.MAIN` из `figma_renders` (`ensure_renders(fetch=False)`),
новый рендер из списка не запрашивается никогда — рендеры Figma
остались за превью слайдов в редакторе, где текст на картинке
и есть то, ради чего туда пришли.

**Кэшируются БАЙТЫ картинки, а не ссылка, и на сутки.** Ссылку Figma
держит около часа: суточный кэш ссылки означал бы битые картинки
через час — ссылка протухла, а мы её всё ещё раздаём. Скачивание
самой картинки идёт с файлового хранилища и квоту не тратит; квоту
тратит только запрос ссылки, раз в сутки на товар.

**Подпись PNG проверяется в `node_png()`, до экрана.** Streamlit
отдаёт байты в PIL, и на обрезанном ответе падает ВСЯ страница —
список товаров уносит миниатюра, которая была лишь удобством.
В списке отказ картинки молчит, в редакторе называется вслух: туда
человек пришёл именно за контекстом.

**Строки берутся от АНГЛИЙСКОГО исходника, перевод подтягивается
к ним по `slot`.** Не наоборот: строки языка существуют только там, где
дизайнер уже нарисовал эту страницу в макете, а переводить надо как раз
туда, где её нет. Запрос `WHERE lang = <язык>` отдавал пусто, и экран
говорил «текстовых слоёв нет» у товара, где их 33 (у B0G4S9SJ3M нет
испанской страницы вовсе) — то есть страница умела показывать только
уже переведённое.

По той же причине правка и перевод модели ВСТАВЛЯЮТ строку, а не
только обновляют: `UPDATE` несуществующей строки молча не делает
ничего, и правка исчезала бы вместе с вкладкой. Исходник и `layer_id`
копируются у английской строки того же места — второе нужно плагину,
чтобы знать, откуда брать слой.

**Правка уезжает в базу сразу, без кнопки «Сохранить».** Кнопка
означала бы, что часть работы живёт только в браузере: вкладку
закрыли — правок нет. Строк здесь десятки, подтверждать каждую
бессмысленно. Сбой записи говорит об этом вслух и советует
скопировать текст: молча потерянная правка хуже видимой ошибки.

**Отказ модели обязан доходить до экрана, и это НЕ бесплатно.**
Кнопка перевода работает колбэком, а из колбэка `st.error` на экран
не попадает — Streamlit рисует элементы позже. Ошибка `services/ai`
при этом оседает только в `last_call_error()`, который читал один
Синтез. Выходил худший вид отказа: кнопка нажата, счётчики нули,
объяснения нет. Теперь всё, что надо сказать, кладётся в
`session_state` и выводится при отрисовке, и три случая различаются:
провайдер не ответил, ответ пуст, места из ответа не совпали
с макетом. Удача тоже называется — сколько строк и какой моделью.

**«Только английский» значит «переводов НЕТ», а не «ни один язык
не доделан».** 25.09, после первого чтения с модулями A+, три
воздуходувки стали в списке английскими — при 97 переведённых строках
из 107 на ES и IT. Проверка по базе показала, что цело всё: `Main
Images` 30 из 30, слоты сошлись, дыры только в новых модулях A+.
Неверным был ярлык: язык считался готовым лишь при нуле пробелов,
а состояний три — и товар, у которого ни один язык не доделан,
попадал в ту же корзину, что товар, где не начинали. Теперь «только
англ.» — это ноль переведённых строк, «все языки» — ноль пробелов
(как было), между ними «частично», и чип говорит числом: «ES 97/107».
Подсказка чипа разносит покрытие по типам мест — «Карточка 30/30 ·
A+ 67/77»: без этого дизайнер ищет пропущенное по всей карточке,
хотя слайды переведены целиком. Считает `lang_coverage()` одним
запросом на весь список; `lang_gaps()` — та же величина в виде
пробелов, от неё живут кнопки и планы перевода.

**«Язык готов» считается ПО СТРОКАМ, а не по факту «хоть одна
переведена».** Первая версия брала `array_agg(DISTINCT lang)` по
непустым переводам: единственная строка, переведённая кнопкой ↻,
красила язык в готовый у товара с тридцатью непереведёнными (живой
случай: B0GTW2CTWZ, DE 1 из 30), и список говорил «все языки
готовы» там, где не сделано ничего. Теперь `lang_gaps()` считает
на каждый язык число английских строк без перевода (служебные —
числа, коды моделей — не в счёт, их не переводит никто), и готов
тот язык, где это число ноль. От того же счёта питается всё: чипы
в списке, язык, на котором «Открыть» откроет редактор, «Все без перевода» и главная
кнопка редактора.

**В редактор ведут название товара, чипы языков и кнопка «Открыть» —
все только ОТКРЫВАЮТ, модель не зовут.** Кнопка называлась «Перевести
· ES», хотя переводит лишь кнопка внутри редактора: подпись принимали
за запуск модели, и веб-агент 27.09 держал её в запрещённых — в
редактор не попал вовсе, название было некликабельным. Потом она
стала «Открыть · ES», и это тоже путало: у стаплера жёлтые ES 31/85
и FR 31/85, а кнопка называла только ES. Теперь кнопка — просто
«Открыть» (на первом языке с работой; основная, пока работа есть),
название — кнопка-ссылка, а чипы языков — кнопки: нажал «FR 31/85»,
редактор открылся на FR. Все входы — один колбэк `_open_product`.

Он же чинит старую ошибку: язык редактора задают галочки языков
(`pick_langs`), а они помнят прошлый заход (правило 7б) — после
первого открытия на DE любой вход, в том числе «Открыть · ES»,
открывал снова DE. Вход кладёт набор `loc-langs-preset` и растит
поколение `loc-langs-gen`, галочки создаются заново на нужном языке.
Тест: DE → назад → FR → назад → ES открывает каждый свой язык, модель
при кликах не вызывается.

**Главная кнопка редактора — «Перевести всё, чего нет».** Она сама
находит непереведённые строки на КАЖДОМ языке, где их нет, и
переводит разом — без выбора языка и переключений. Строки на
каждый язык СВОИ (`missing_plan`): у DE может не хватать тридцати,
у FR одной, и общий список переводил бы заново то, что уже есть.
Галочки языков на неё не влияют — они для «заново» и для
просмотра. Когда не хватает ничего, кнопки нет, а не «Перевести
0 строк»: вместо неё сказано, что переводить нечего.

**Массовая работа — в списке, по отмеченным товарам.** Раньше всё
шло по одному: открыл, перевёл, вернулся, открыл следующий — четыре
товара на четыре языка это шестнадцать заходов. Отметки живут
НАБОРОМ `loc-sel` в `session_state`, а не в ключах галочек: «Выбрать
все» стоит выше галочек и переставить их напрямую не может (правило
7б) — кнопка меняет набор и растит поколение `loc-sel-gen`. Над
списком две кнопки по выбранным. «Перевести всё, чего нет · 142
строки, 4 товара, 2 языка» — число считается от `lang_gaps` без
походов в базу, и это не «выбрано 4», а «4, у которых есть работа».
Идёт не колбэком, а прямым вызовом с `st.status`: двадцать товаров
на четыре языка это минуты, и молчащий экран не отличить от
сломанного; итог кладётся в `session_state` и рисуется после
rerun. «Выгрузить для Figma · 310 строк, 4 товара» — ОДИН файл
`{"file_key", "items": [{"asin", "lang", "layers"}]}` вместо файла
на товар и язык; плагин принимает обе формы. Оба пути перевода —
редактор и список — идут через `_run_plan`, который сам ничего
не говорит: говорят вызывающие, каждый по-своему.

**«Перевести заново» есть и у строки, и у товара.** Переделать чаще
надо одну строку, а не карточку целиком — это дешевле по времени
и по деньгам. Дорога у всех кнопок одна — `_translate_plan`, план
`{язык: строки}`; разница только в том, кто план собирает.

Подписи кнопок — СЛОВАМИ: «Перевести заново 22 строки на
французский», «…на 3 языка». Было «Перевести · 22 × 1», и
произведение читалось как формула — спрашивали, что умножается.
Склонение даёт `i18n.plural(key, n)` по формам `key.one/few/many`.

Кнопки товара — НАД таблицей, первой строкой, как массовые действия
на Синтезе: строк три десятка, и под ними кнопка уезжает за экран.
Её уже считали пропавшей и жали ↻ на каждой строке. Под таблицей
остаются только оговорки про расчётный предел — они поясняют
колонку длины и стоят рядом с ней.

**Промпт виден целиком и правится руками** — expander «Настроить
перевод». Скрытый промпт это чужие решения, которые нельзя оспорить:
дизайнер дописывает «не переводить название модели» туда же, а не
пишет о нём в чат. Хранится в `synthesis_skill` со `scope='translate'`,
до первого сохранения показывается текст по умолчанию И ОБЪЯВЛЯЕТСЯ
несохранённым.

**Служебные строки не переводятся и свёрнуты.** Числа с единицами
(«2 Ah», «11–13 min», «240 km/h») и коды моделей («BP-220»,
«BP-240/240N») одинаковы на всех языках: из 153 строк первого захода
таких 42, почти треть таблицы. В модель они не уходят, на экране
лежат отдельным свёрнутым блоком с пометкой «перевод не нужен»,
и в подписи кнопки стоит число строк, которые РЕАЛЬНО уйдут.

Граница проходит по признакам, а не по списку слов, и проверена
фактом: «Capacity» и «Speed I» выглядят такими же служебными, но
в макетах ПЕРЕВЕДЕНЫ («Capacidad», «Velocidad I»). Единицы поэтому
перечислены списком: «30 shots/min» стало «30 Schuss/min» — единица
тут слово, и она переводится.

**Языки выбираются НЕСКОЛЬКО сразу** — чекбоксы плюс «все, где нет
перевода»: перевод товара на четыре рынка это одна работа, а не
четыре захода. Глоссарий берётся свой на каждый язык (словарь
дизайнера у немецкого и итальянского разный), а отказ по одному
языку не выдаётся за отказ по всем: на экране и сделанное, и
несделанное своим числом.

**Глоссарий собирается сам** из готовых переводов: строка, которая
есть и на UK/US, и на DE, — уже пара, связанная по `slot`. Пары идут
в промпт образцом стиля, включая совпадающие с исходником: коды
моделей и «1,500 mAh» не переводятся, и модель должна это видеть.

**След модели хранится рядом с переводом** (`model_text`, `model`,
`edited_after_model`). Правка человека определяется СРАВНЕНИЕМ
с текстом модели, а не фактом открытия поля, и через месяц ответит,
где перевод можно отдать автоматике. Перевод моделью не затирает
строки, которые человек уже поправил.

Картинки не хранятся: оригиналы остаются в Figma, готовые файлы
в Drive, в базе только текст и ссылки. Запись в Figma через REST
невозможна (API умеет только читать) — нужен плагин, поэтому
«Применить в Figma» отдаёт JSON с переводами для плагина, а не
висит неактивной кнопкой с объяснением.

**Плагин — в [figma-plugin/](../figma-plugin/)**, три файла без сборки
(`manifest.json`, `code.js`, `ui.html`), ставится через «Import
plugin from manifest». Связка по `slot`, не по `layer_id`: id узлов
на языковых страницах другие, а имена фреймов и пути совпадают —
33 из 33 у B0G4S9SJ3M на UK/US и DE. `PAGE_LANG` и `FRAME_RE`
продублированы в `code.js` и заперты тестом на равенство с
`services/figma.py`. Страница ищется по имени БЕЗ хвостовых пробелов
и регистра (`page_lang` / `pageLang`): точное сравнение 19.09
отвечало «Языковой страницы DE в файле нет» при открытой DE.
Отказ теперь перечисляет страницы файла как их видит плагин —
расхождение имени видно сразу. Плагин не трогает картинки, шрифт и кегль,
не создаёт слои и не применяет молча: план → кнопка → отчёт из трёх
чисел, где «не найдено слоёв» важнее «заменено». Первая версия
работает только с готовыми языковыми страницами (их 11);
копирование макета на новую страницу — следующий шаг, см. README.

**Переводы попадают в плагин ВСТАВКОЙ из буфера, а не файлом и не
по сети.** Рядом с кнопкой выгрузки — и в списке, и в редакторе —
блок `st.code` с тем же JSON: у него штатная иконка «скопировать»,
дизайнер вставляет текст в поле плагина. Убрано главное трение
файла — «скачать, найти в папке, загрузить», — без новой
инфраструктуры. Файл остался вторым путём.

Забор по сети пробовали и сняли: маршрут внутри Streamlit
(`st.App`) на Cloud недостижим — приложение закрыто авторизацией,
прокси не пускает плагин. Следующий шаг, когда до него дойдёт, —
ПУБЛИКАЦИЯ через Drive: приложение кладёт JSON в папку, которой
владеет наш сервисный аккаунт (свою, а не «Категорії» — доступа
не нужно), с чтением по ссылке; плагин по кнопке скачивает файл
по id. Условие, чтобы браться: подстановка в макет проверена
на живых карточках. Данные по ссылке читает любой, кто знает id;
это тексты карточек, не секрет — но решение принимается вслух.

**Первый заход — четыре товара, а не весь файл.** Галочка «пробный
заход» включена по умолчанию и режет чтение до `FIRST_PASS_ASINS`:
у этих четырёх есть готовые переводы, из которых сразу собирается
глоссарий. Ограничение снимается галочкой, а не правкой кода —
решение «идём на весь файл» принимает человек, когда убедится, что
перевод годный. Список из четырёх ОБЪЯВЛЯЕТСЯ неполным плашкой: иначе
по нему начнут считать объём работы, как по демо-данным (в файле 21
товар и 1163 слоя против 459 у пробного набора).

**Чтение из Figma — раз в сутки или по кнопке.** Не из экономии:
при исчерпанном лимите Figma отвечает 429 и просит ждать сотни секунд
на КАЖДУЮ попытку, поэтому ретраев в коде нет вовсе — наверх идёт
время ожидания, и человек решает сам. Документ читается целиком одним
запросом и раскладывается в базу; дальше страница работает из базы,
а метка `synced_at` живёт в самих данных, а не в кэше процесса —
процесс на Cloud перезапускается, и кэш в памяти заставлял бы читать
Figma заново после каждого перезапуска.
Читает: `figma_products`, `figma_layers`, `synthesis_skill` (промпт).
Пишет: `figma_layers` (перевод, след модели), `synthesis_skill`.

### `content.py` → «Паспорт SKU» (`components/passport_area.py`) — этап 1

Вторая вкладка Контента. Внутри — три вкладки v1: Реестр Паспортов, Создание
Паспорта, Взаимодействие с Верификатором. Этап 1 — только чтение, все
изменяющие действия выключены и называют свой флаг (`FEATURE_DISABLED`).

**Вкладки — сегмент с ключом `pp-tab`, а не `st.tabs`.** ТЗ требует из
Реестра попадать СРАЗУ в нужную вкладку к нужному объекту: «Ответить»
открывает Верификатора на точном `Q-…`, а `st.tabs` из кода не
переключается. Контекст — `pp-sku` в `session_state`. Он стоит в заголовке
каждой вкладки (ТЗ §8), карточка Реестра показывается по нему же, и после
возврата из другой вкладки товар тот же. Смена товара только явная —
кнопкой «Сменить товар».

**У строки Реестра четыре независимые оси, в порядке ТЗ 9.6.5:**
идентичность → актуальность данных → состояние Паспорта → нужно ли моё
действие. Следующее действие одно и считается после всех четырёх (9.7). Три
правила ломаются тихо и заперты `test_passport_registry.py`:

- `BLOCKED` — только при действующем блокере `BLK-<RUN>-<NNN>` с причиной,
  ответственным и условием возобновления. Записанное BLOCKED без блокера и
  отправленный вопрос без блокера — это «В работе»; у вопроса отдельно
  стоит «Требуется ответ».
- «Паспорт отсутствует» — результат поиска, а не пятое состояние: машинный
  `state` пуст.
- SHA Паспорта не подтверждён системной сверкой (`readback_sha256`) — «Данные
  устарели». Изменяющие действия заперты, статус Паспорта при этом не
  меняется.

**Возможный дубликат — тот же EAN или ASIN у двух SKU справочника.** Он
запирает всё до выбора точного SKU — так рядом с базовым 21680000 ловится
метка акции «21680000-4». Привести метку к базовому — решение Верификатора,
не Реестра. Поиск по названию SKU не подтверждает: строки показываются, но
действие появляется только у выбранного товара.

**Сбой чтения — «Ошибка загрузки» и последнее подтверждённое состояние с
датой.** Пустоты при сбое нет, «Создать Паспорт» не предлагается. Нет
миграции — страница жива и называет файл.

### `textgen.py` — «Генератор текстов (пилот)», каркас без модели (21.10.2026)
Пять пилотных товаров ES: характеристики с источником каждого значения, ключи по
типу, тайтл и Highlights руками с живой проверкой `title_rules.check()`. Модель не
вызывается. Пишет только копию паспорта docx в том UC (`services/passport_copies.py`).
Подробно — [docs/textgen.md](textgen.md).

### `matrix_setup.py` — «Матрица товаров»
Ввод ASIN пачкой (терпимый парсер: `sku, asin, mp[, конкурент]`, голый ASIN,
URL Amazon), импорт из зеркала каталога, список карточек с кнопкой «Собрать»,
групповые действия, удаление, расписание автосбора.
**Здесь живёт рабочий пайплайн сбора** — `collect_rows()`: запрос к ScrapingDog
(с `country` и `language`; без `country` фолбэк «us» уводит сбор
на amazon.com и снапшот приезжает от чужого листинга, без `language`
amazon.es отдаёт EN-версию и длина тайтла считается по чужому языку) → запись снапшота → запись длин → создание болей по правилам
`out_of_stock`, `title_over_limit`, `low_reviews`, `few_images`, `no_video`,
`no_aplus`.
Читает: `product_matrix`, `listing_snapshots`, `diagnosis`, `catalog_source`,
`collection_schedule`.
Пишет: `product_matrix`, `listing_snapshots`, `listing_analysis`, `diagnosis`,
`collection_schedule`.

### `methodology.py` — «Методологии»
Библиотека скиллов с версиями. Каждая область (`scope`: `common`,
`title_split`, `bullets`, `photo_brief`, `aplus`, `ai_grade`, …) — своя
методология. Правки без коммитов кода: новая версия при каждом сохранении,
откат в один клик. Здесь же редактируются пороги правил (лимиты, min_reviews,
min_images, границы рейтинга) и ведётся реестр источников политик Amazon
с алертами об изменениях.
Читает: `synthesis_skill`, `policy_sources`, `policy_alerts`, `app_settings`.
Пишет: `synthesis_skill`, `policy_sources.last_checked`, `policy_alerts.status`,
`app_settings`.

### `settings.py` — «Настройки»
Четыре блока: статус подключений (Gemini, Anthropic, ScrapingDog,
Amazon SP-API, Lakebase — маска ключа + кнопка проверки связи; у SP-API
ключей четыре, поэтому называется каждый недостающий, а проверка дёргает
`GET /sellers/v1/marketplaceParticipations` и показывает число рынков
и подавленные листинги), выбор провайдера и модели под каждую
задачу `services/ai.py` (`title_split`, `photo_audit`, `agents`,
`translate`; списки моделей тянутся живьём из API провайдеров). Список
задач живёт в ДВУХ местах — `DEFAULTS` в `services/ai.py` и `TASKS`
здесь, — и их согласованность проверяет `test_ai_errors`: разошлись,
и задача работает по умолчанию из кода, которое никто не выбирал
и изменить не может, загрузка эталонов flat file
и ссылка на пороги правил (они живут в «Методологии»). Ключи API здесь
не хранятся и не вводятся — только в Streamlit Secrets, наружу идёт лишь
хвост ключа.
Читает и пишет: `app_settings` (через `services.settings`),
`flatfile_templates` (через `services.flatfile_template`).
