# Автономная работа Listing Suite: схема (предложение 19.10.2026)

Правила в коротком виде — AGENTS.md, раздел «Автономия». Здесь — как это
устроено и почему так. Схема повторяет Кабинет (kabinet-dashboard PR #328,
`docs/autonomy.md` там же); отличия Listing Suite названы ниже.

## Зачем

Раньше каждый шаг ждал владельца. Мерж любого PR, включая документацию,
шёл только по «мержи #N». О готовности агент сообщал в чат, где сообщение
тонет.

Владелец хочет, чтобы рутина шла сама: он видит итог и решает только то,
что требует решения. Цена ошибки при этом разная:

- опечатка в `docs/` безвредна;
- правка кода меняет то, что видит команда;
- отправка в Amazon меняет живой листинг клиента;
- вызов модели стоит денег;
- правка канона Ярослава нарушает прямой запрет владельца процесса.

Отсюда три уровня, а не одно общее правило.

## Четыре части

1. **`TASKS.md` — очередь.** У каждой задачи — уровень и проверяемый
   критерий готовности. Например: «вес 8,2 кг, а 7,5 отклонён», а не
   «сделать приёмку». Агент может поднять уровень, опустить — только
   владелец. Это и есть договор: всё, чего нет в очереди, агент сам не
   начинает.
2. **Уровни в AGENTS.md** — «сам», «ждёт меня», «никогда сам». Уровень
   считается по ИЗМЕНЕНИЮ, а не по задаче. Задача «добавить перевод» может
   притащить правку страницы, и тогда PR целиком становится «ждёт меня».

   Уровень «сам» узкий, и его граница проверяема по diff — это и делает
   проверяющий:
   - `docs/` — только добавление;
   - `TASKS.md` — без понижения уровней;
   - комментарии;
   - недостающие переводы без смены смысла;
   - проверочные скрипты только на чтение.

   Проверяющий, `docs/autonomy.md` и сам раздел «Автономия» — только
   «мержи»: агент не расширяет себе права.
3. **Агент-проверяющий** — `.claude/agents/pr-reviewer.md`, отдельный
   агент, который не писал PR. Он:
   - читает diff и правила;
   - определяет уровень изменения;
   - идёт по списку типовых поломок проекта (NaN из pandas, строки мимо
     `t()`, HTML в несколько строк, ключ виджета против `value`, фильтр из
     двух источников, «пусто» против «сломалось», колонка без
     `missing_columns`, `ast.parse` вместо `compile`);
   - прогоняет весь `tests/`;
   - пишет вердикт комментарием в PR.

   Почему отдельный агент: автор проверяет то, что помнит, а пропускает
   как раз то, что забыл. Вердикт в PR, а не в чате, — чтобы владелец
   видел его там, где мержит.
4. **Сводка в бот после цикла.** Агент кладёт строку в
   `kabinet_data.agent_cycle_reports` (`scratchpad/cycle_report.py`):
   - что сделано;
   - что смержено само;
   - что ждёт владельца;
   - что не получилось.

   Задача Кабинета «Kabinet - Agent Cycle Report» каждые 15 минут
   08:00–22:45 отправляет неотправленное в тот же бот.

## Чем Listing Suite отличается от Кабинета

- **Бот, таблица и задача отправки — Кабинета.** Своих у Listing Suite нет
  и не нужно: владелец один, бот один. Шапка сводки получает приставку
  «Listing Suite · ». Запись идёт под ролью Кабинета из его `.mcp.json`.
  Поэтому сводка заработает только после мержа kabinet-dashboard #328 и
  применения его SQL.
- **«Никогда сам» шире.** К секретам, входу и удалению добавлены:
  - **Канон Ярослава** — только чтение. Это решение владельца процесса
    AI Design, а не наше, поэтому не «ждёт меня»: разрешить правку не
    может и владелец Listing Suite. Обновление снимка прогоном
    `build_snapshot.py` по новому архиву Ярослава — не правка, это
    «ждёт меня».
  - **Отправка в Amazon** — пишет в живые листинги клиента.
  - **Вызовы моделей и всё, что тратит деньги или невосполнимую квоту**:
    генерация, перевод, аудит фото, агенты Паспорта, сбор ScrapingDog,
    запуск сборщика, запросы к Figma (6 в месяц на месте View).

  Тесты с подменённым провайдером разрешены и нужны: именно ими агент
  проверяет такой код, не тратя денег.
- **Миграции SQL и ребут Streamlit Cloud — «ждёт меня».** Миграция
  приходит PR, а применяется в Databricks отдельным словом владельца.
  Ребут делает владелец; агент только называет, когда он нужен (новые
  символы в `services/*`, новые ключи `i18n`).
- **Окон без мержа нет.** У Кабинета они защищают утренние и вечерние
  цепочки загрузки. У Listing Suite сам сливается только то, что не меняет
  работу приложения, а код и миграции идут по слову владельца — время
  выбирает он.
- **AGENTS.md не сжимался.** У Кабинета он был 390 тыс. символов и ушёл в
  `docs/`. Здесь 133 тыс., меньше порога в 150 тыс.: сжатие без нужды
  только разнесло бы правила по файлам. Порог перерастёт — переносить
  разделы страниц и модулей в `docs/` дословно, со сверкой строк.

## Цикл

1. Прочитать `TASKS.md`, открытые PR и комментарии проверяющего.
2. Взять задачи по порядку очереди. «Ждёт меня» — довести до PR с
   проверкой и описанием «что проверено, что нет».
3. Проверяющий на каждый PR. Замечания — исправить, проверить заново.
4. Смержить только уровень «сам» с вердиктом «ок». Остальное — в «Ждёт
   вас» сводки.
5. Обновить `TASKS.md`.
6. Сводка в бот.

## Что сознательно НЕ автоматизируется

- Мерж кода, миграций, настроек и правил — по-прежнему «мержи #N». Тесты
  ловят падения, но не неверные решения.
- Канон, Amazon, модели и траты, секреты, вход, удаление данных,
  сообщения людям — «никогда сам».
- Изменение самого раздела «Автономия» — только по «мержи»: агент не
  расширяет себе права.

## Как включить

1. Мерж kabinet-dashboard #328, его SQL
   (`sql/agent_cycle_reports_2026-10-19.sql`) и задача «Kabinet - Agent
   Cycle Report» — по инструкции того PR.
2. Мерж этого PR.
3. Пробная сводка:

   ```
   python3 scratchpad/cycle_report.py --title "Пробная сводка" --done "схема автономии включена"
   ```

   Она должна прийти в бот с шапкой «Listing Suite · Пробная сводка».
