# «Контент → Паспорт SKU»: канон конвейера и порядок работы — подробно

Перенесено из AGENTS.md 21.10.2026 дословно, раздел ««Контент → Паспорт SKU»: канон конвейера и порядок работы (с 07.10.2026)» (решение владельца: в AGENTS.md — правила и ссылки). Ссылки поправлены под папку `docs/`; содержание не менялось.


Область строится по «Функциональному ТЗ Listing Suite → Контент → Паспорт SKU»
v1.0 (04.10.2026) и канону конвейера AI Design. Канон ведёт владелец процесса
AI Design (Ярослав), и это не наш код.

**Канон только читаем.** Решение владельца: ИИ в каноне конвейера ничего не
меняет и не добавляет. Нужная Listing Suite часть лежит снимком в
[canon/](../canon/README.md): копия байт в байт, `MANIFEST.json` с SHA-256 каждого
файла и самого архива. Правку и лишний файл ловит `test_canon_snapshot.py`.
Обновляется снимок только прогоном `canon/build_snapshot.py` по новому
архиву от владельца. Расхождения внутри канона — ссылка цитирует v1.1 при
файле v1.2, реестр рёбер без полей, которые контракт графа объявил
обязательными, схема запуска с путём диска Windows — не чинятся, а
называются в `canon/REFERENCE_DRIFT.md` и уходят владельцу. Код берёт ФАЙЛ
из снимка, а не версию из ссылки.

Из нескольких версий одного документа в снимок идёт последняя. Старые
остаются только там, где новая стоит на них по SHA («byte-addressed»): 06F
v1.3 наследует v1.2, та — v1.1, и без родителя набор не исполним. Архивы,
эскизы PNG и конфигурация FULL (05–05C — Координатор v2.9 её исключает) в
снимок не входят.

**Договорённости 07.10.2026, которых в каноне нет:**

- v1 — три вкладки: Реестр, Создание, Взаимодействие с Верификатором.
  Image Collection — после v1.
- v1 только Amazon. Требования площадок берутся только из
  `marketplace_requirements_registry.json`. Нет профиля —
  `LOCALE_REQUIREMENTS_PENDING` и `BASE_TZ_ONLY`; правил из памяти модели нет.
- Движок графа и вызовы модели — наши: задача Databricks из git.
  Канонические инструкции агентов идут в модель из снимка без изменений.
- Обратные рёбра канона (E035, E050, E080 и другие) — зарегистрированные
  рёбра с бюджетом. Циклов в коде нет, исчерпание бюджета даёт
  `FAILED_EXHAUSTED`. Это и есть «граф, не циклы».
- Модель выбирается настройкой (OpenAI или Claude). Лимит вызовов и денег на
  запуск обязателен, значения — в `app_settings`.
- Загрузка: файлы, ZIP и ссылка на папку Google Drive (разовый снимок через
  design@dniprom.com).
- Рабочая копия и SHA — на томе UC, человеку — папка на Drive.
- Реестр начинается пустым. Пилотные Паспорта DHR-203BCV и 21680000 —
  эталоны для сверки, а не импорт.
- Справочник SKU — база Кабинета. Привязки прав к SKU (LS-CFG-005) в v1 нет.
- Палитра — наша (правило 6), эскизы только по раскладке.
- Приёмка №1 — PW-14B (SKU 21680000) против эталонной папки владельца.

**Порядок работ — этапы Delivery Package, каждый отдельным PR, мерж по
команде.** 0 — снимок канона, миграция, контрактные тесты. 1 — область
только на чтение. 2 — движок графа в теневом режиме. 3 — Создание.
4 — Верификатор. 5 — новые данные и пересоздание. 7 — включение флагов
отдельными квитанциями. Все изменяющие действия до своей квитанции
отвечают `FEATURE_DISABLED`.

**Хранилище — миграция `2026-10-07_passport_sku_core.sql`, девять таблиц.**
Шесть принадлежат Паспорту (`passport_*`), три — движку графа и общие:
`ai_runs`, `ai_run_events`, `ai_receipts`. Граф AI Design один, и запуск
«Контента» продолжается в нём же: ребро E140 выходит из координатора
Паспорта N020. Свои таблицы у каждой области означали бы два движка,
которые расходятся. Область запуска — колонка `ai_runs.route`, «Контент»
расширит её CHECK своей миграцией. Статусы — закрытые словари из канона дословно, и
`test_passport_vocab.py` сверяет каждый CHECK с текстом 00A, 06E, ТЗ и схемы
run_state. Три инварианта держит база, а не код:

- у SKU ровно один ACTIVE Паспорт — частичный уникальный индекс;
- история запуска, квитанции, ответы и вердикты только дописываются —
  триггер;
- повтор с тем же idempotency key не создаёт второй записи — UNIQUE.
