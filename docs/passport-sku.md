# «Контент → Паспорт SKU»: канон конвейера и порядок работы — подробно

Перенесено из AGENTS.md 21.10.2026 дословно, раздел ««Контент → Паспорт SKU»: канон конвейера и порядок работы (с 07.10.2026)» (решение владельца: в AGENTS.md — правила и ссылки). Ссылки поправлены под папку `docs/`; содержание не менялось.


Область строится по «Функциональному ТЗ Listing Suite → Контент → Паспорт SKU»
v1.0 (04.10.2026) и канону конвейера AI Design. Канон ведёт владелец процесса
AI Design (Ярослав), и это не наш код.

**Канон только читаем.** Решение владельца: ИИ в каноне конвейера ничего не
меняет и не добавляет. Нужная Listing Suite часть лежит снимком в
[canon/](../canon/README.md): копия байт в байт, `MANIFEST.json` с SHA-256 каждого
файла и самого архива. Правку и лишний файл ловит `test_canon_snapshot.py`.
Обновляется снимок только прогоном `canon/build_snapshot.py` по новому
архиву от владельца. Расхождения внутри канона — ссылка цитирует v1.1 при
файле v1.2, реестр рёбер без полей, которые контракт графа объявил
обязательными, схема запуска с путём диска Windows — не чинятся, а
называются в `canon/REFERENCE_DRIFT.md` и уходят владельцу. Код берёт ФАЙЛ
из снимка, а не версию из ссылки.

Из нескольких версий одного документа в снимок идёт последняя. Старые
остаются только там, где новая стоит на них по SHA («byte-addressed»): 06F
v1.3 наследует v1.2, та — v1.1, и без родителя набор не исполним. Архивы,
эскизы PNG и конфигурация FULL (05–05C — Координатор v2.9 её исключает) в
снимок не входят.

**Договорённости 07.10.2026, которых в каноне нет:**

- v1 — три вкладки: Реестр, Создание, Взаимодействие с Верификатором.
  Image Collection — после v1.
- v1 только Amazon. Требования площадок берутся только из
  `marketplace_requirements_registry.json`. Нет профиля —
  `LOCALE_REQUIREMENTS_PENDING` и `BASE_TZ_ONLY`; правил из памяти модели нет.
- Движок графа и вызовы модели — наши: задача Databricks из git.
  Канонические инструкции агентов идут в модель из снимка без изменений.
- Обратные рёбра канона (E035, E050, E080 и другие) — зарегистрированные
  рёбра с бюджетом. Циклов в коде нет, исчерпание бюджета даёт
  `FAILED_EXHAUSTED`. Это и есть «граф, не циклы».
- Модель выбирается настройкой (OpenAI или Claude). Лимит вызовов и денег на
  запуск обязателен, значения — в `app_settings`.
- Загрузка: файлы, ZIP и ссылка на папку Google Drive (разовый снимок через
  design@dniprom.com).
- Рабочая копия и SHA — на томе UC, человеку — папка на Drive.
- Реестр начинается пустым. Пилотные Паспорта DHR-203BCV и 21680000 —
  эталоны для сверки, а не импорт.
- Справочник SKU — база Кабинета. Привязки прав к SKU (LS-CFG-005) в v1 нет.
- Палитра — наша (правило 6), эскизы только по раскладке.
- Приёмка №1 — PW-14B (SKU 21680000) против эталонной папки владельца.

**Порядок работ — этапы Delivery Package, каждый отдельным PR, мерж по
команде.** 0 — снимок канона, миграция, контрактные тесты. 1 — область
только на чтение. 2 — движок графа в теневом режиме. 3 — Создание.
4 — Верификатор. 5 — новые данные и пересоздание. 7 — включение флагов
отдельными квитанциями. Все изменяющие действия до своей квитанции
отвечают `FEATURE_DISABLED`.

**Хранилище — миграция `2026-10-07_passport_sku_core.sql`, девять таблиц.**
Шесть принадлежат Паспорту (`passport_*`), три — движку графа и общие:
`ai_runs`, `ai_run_events`, `ai_receipts`. Граф AI Design один, и запуск
«Контента» продолжается в нём же: ребро E140 выходит из координатора
Паспорта N020. Свои таблицы у каждой области означали бы два движка,
которые расходятся. Область запуска — колонка `ai_runs.route`, «Контент»
расширит её CHECK своей миграцией. Статусы — закрытые словари из канона дословно, и
`test_passport_vocab.py` сверяет каждый CHECK с текстом 00A, 06E, ТЗ и схемы
run_state. Три инварианта держит база, а не код:

- у SKU ровно один ACTIVE Паспорт — частичный уникальный индекс;
- история запуска, квитанции, ответы и вердикты только дописываются —
  триггер;
- повтор с тем же idempotency key не создаёт второй записи — UNIQUE.

## Один паспорт на SKU: раздел и генератор (28.10.2026)

Чеклист владельца 28.10.2026 для «Создания Паспорта». Аудит показал, что раздел и
генератор жили на разных источниках: раздел читал только `passport_objects` (0 строк),
генератор — копии docx в `passport_source_artifacts`. Отсюда «Паспорт отсутствует» у
99601000-B при действующей копии v2.

- **Источник один.** `services/passport.load_registry` берёт и `passport_objects`, и
  действующие копии паспорта docx (тип docx и место в томе `passports` — та же
  область, что у `passport_copies.register`). Копия становится строкой Реестра того
  же вида: состояние, версия, id — из шапки, модель и название — из раздела
  идентичности. SHA копии подтверждён при регистрации (повторное чтение тома),
  поэтому свежесть — «актуально». Если у SKU есть и строка `passport_objects`, и
  копия, главнее строка движка. Второй паспорт на SKU не создаётся: у SKU с копией
  «Создать Паспорт» не предлагается. Не прочитался том — паспорт показан, причина
  названа, свежесть не подтверждена.
- **Поиск** по SKU, названию, модели, ASIN и EAN находит паспорт-копию: модель — из
  копии, остальное — из справочника Кабинета.
- **«Создание»** для SKU с копией говорит, что паспорт есть и генератор работает по
  нему. Загрузка docx — тот же блок, что в генераторе (`components/passport_upload.py`):
  копия в томе, заморозка, «заменить?». «Собрано по SKU» показывает без ручного
  ввода название, EAN, ASIN, ASIN ES, тип, модель, характеристики с источником
  каждого значения, текущий тайтл и комплект. Руками — только недостающие
  материалы, комментарий-контекст и решения по конфликтам.
- **Карточка паспорта** (Реестр → «Открыть Паспорт») показывает комплектацию с
  количествами и конфликты: статус в паспорте, состояние (открыт / закрыт в паспорте /
  решён верификатором), решённое значение и источник решения.
- **Верификатор** закрывает конфликт копии: сторона A, сторона B или своё значение
  и ПРОВЕРЯЕМЫЙ источник («чат 21.10, Ярослав»). Решение пишется строкой в
  `passport_conflict_decisions` (миграция `2026-10-28_passport_conflict_decisions.sql`,
  только дописывание — триггер), копия паспорта не меняется. Право —
  `ls.textgen.accept`; `ls.passport.decide` — когда привяжется канонический профиль
  полномочий. Без миграции кнопка выключена и называет файл.
- **Решение привязано к копии и её SHA.** Новая копия (v3) приходит со своими
  конфликтами, решения по v2 к ней не относятся. Действует последнее решение по
  конфликту.
- **Чего нет.** Настоящая сборка паспорта по канону — агенты Ярослава — по-прежнему
  выключена: нужны `product_root`, привязанный профиль полномочий и квитанции этапа 7.
  Отмены решения нет: исправление — новым решением.
- **Уточнения после проверки #176.** Сбой чтения тома не кэшируется: починили том —
  паспорт читается сразу. Причина сбоя — в карточке Реестра. В Реестр идёт только
  действующая копия. Паспорт, который ведёт движок (`passport_objects`), на
  «Создании» docx-копией не дополняется — это был бы второй паспорт. На «Создании»
  чужой по SKU файл не сохраняется. Внешний текст (тайтл, стороны конфликта,
  введённое) на экране экранируется (`components/ui.md_escape`). Время решения
  ставит база — ни в будущем, ни задним числом.

## Выпадающий список товаров в Реестре (28.10.2026)

Поручение владельца 28.10.2026: выбирать товар списком, а не обязательным ручным поиском.

- **Список тянется сам** из справочника SKU Кабинета (`passport.sku_directory`, только
  чтение); руками товары в него не вводятся. В строке — SKU, название, тип и статус
  паспорта: «паспорт v2, «В работе»» или «Паспорт отсутствует».
- **Выбор в списке — точный выбор SKU** (`pp-sku`), тот же, что выбор строки Реестра:
  его видят «Создание», карточка паспорта, «Верификатор» и генератор. Карточка
  показывается и для товара, которого нет в текущем поиске. Ключ виджета несёт SKU
  контекста: выбор в другом месте пересоздаёт список на нём (правило 7б). Выделение
  строки таблицы применяется только при смене — не перебивает выбор из списка.
- **Тип — из данных товара**: листинг ES (тайтл последнего снапшота и productType), тем
  же `product_specs.detect_type`, что у генератора; SKU связан с листингом ASIN
  справочника, что стоит в матрице ES, или точным `sku_group`. Нет листинга ES — «тип
  не определён». Категории ERP Кабинета не читаются (решение 07.10.2026).
- **Тип определяет правила генерации** (`textgen.kind_of`): аккумулятор и зарядка —
  вольтаж в тайтле можно, инструмент и неизвестный тип — нельзя; тип называется в
  промпте. Генератор встаёт на SKU контекста, но выбрать там другой можно.
- Справочник не прочитался — ошибка над списком, в списке остаются товары с паспортом.
  Ручной поиск по SKU, названию, модели, ASIN и EAN — как раньше, запасным путём.
- **Уточнения после проверки #178.** Список заполняется после таблицы: клик по строке
  виден в списке в том же прогоне. Пустой пункт «выберите товар» — явный сброс товара.
  Копия есть, но не прочиталась — «паспорт v…, не прочитан», а не «Паспорт отсутствует».
  Сбой чтения листингов не кэшируется. В генераторе выбор человека хранится отдельно
  от ключа виджета (`tg-gen-choice`) и переживает уход со страницы; новая смена
  контекста ставит генератор на SKU контекста. Отдельное предупреждение о справочнике
  под списком убрано: ошибка одна, над списком.

**Падение Реестра 28.10.2026 после #178.** `TypeError` в `passport.sku_types`: тип, который
`detect_type` не узнал, в столбце DataFrame хранится как NaN (строковый столбец pandas 3),
NaN истинный и проходил проверку `if ty`, а сортировка сравнивала его со строкой. Падало
на SKU, у которого один листинг ES с узнанным типом, а другой — без. Фикстура #178 такой
пары не имела. Починено чтением через `cell_text` (правило 4); тест собирает столбец тем же
`pd.DataFrame(rows, columns=…)`, что код, и падает на прежнем коде.

**Фото товара в карточке Реестра (поручение владельца 28.10.2026).** Рядом с названием в
карточке выбранного товара — фото или заглушка «фото отсутствует» (`passport.sku_photo`,
`passport_area.photo_html`).
- **Источник проверен, а не угадан.** В справочнике Кабинета (`sku_master`,
  `product_entity_listings`) полей фото нет. Фото есть в снапшотах наших листингов:
  `listing_snapshots.raw -> 'images_of_specified_asin' ->> 0` (картинки именно этого
  ASIN). Берётся последний удачный (`ok`) снапшот, только ES, только наш листинг
  (`is_competitor IS NOT TRUE`). Запасной `raw ->> 'main_image'` нет: на 28.10 у 36 из
  305 наших ES-листингов она не совпадает с картинками самого ASIN (проверка #180); без
  неё фото теряют 12 листингов, у которых есть только `main_image`.
- **Связь SKU с листингом — только по ASIN справочника Кабинета**, не по `sku_group`
  матрицы: `sku_group` — группа. Пример: у B0GTRY26HB в матрице `sku_group = 99601000`, а
  продаётся набор 99601000-B (две батареи BP-240 и зарядка FC-230 в буллетах ES); фото по
  группе показало бы чужой товар (путаница JS-8 / JS-16C).
- **Не угадываем:** у SKU несколько ASIN с фото — заглушка, ASIN названы в подсказке.
  ASIN, который справочник Кабинета даёт и другому SKU (наблюдаемые листинги), — не
  фото этого SKU: если других ASIN с фото нет, заглушка с ASIN и вторым SKU в подсказке.
  Ссылка принимается, только если это картинка `https://m.media-amazon.com/images/I/…`;
  пустая, NaN и чужая — заглушка.
- **Заглушка** — серая рамка того же размера (88×88) с текстом «фото отсутствует»;
  причина — во всплывающей подсказке; сбой чтения — ещё и подписью под карточкой. Рамка
  фото задана заранее (медленная загрузка не двигает карточку), `alt` пустой —
  незагрузившаяся ссылка не рисует значок битой картинки, остаётся пустая рамка.
- **Список «Товар» не менялся.** Выпадающий список Streamlit (`st.selectbox`) показывает
  опции только текстом, картинок внутри опций не умеет; фото — только в карточке.
- На 28.10.2026: 99601000-B — фото есть (ASIN B0GTRY26HB, ES, снапшот 28.10), 08087000 —
  нашего листинга ES в Listing Suite нет, заглушка.
