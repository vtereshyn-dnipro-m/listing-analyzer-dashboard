# Модули (`services/`, `components/`) — подробно

Перенесено из AGENTS.md 21.10.2026 дословно, раздел «Модули (`services/`, `components/`)» (решение владельца: в AGENTS.md — правила и ссылки). Ссылки поправлены под папку `docs/`; содержание не менялось.


### `services/db.py`
Подключение (три режима), `cfg()` для секретов, DDL и CRUD `product_matrix`,
парсер ввода `parse_asin_lines()`, `safe_read()` — чтение, отличающее
«пусто» от «сломалось».
Таблицы: `product_matrix`.

`table_exists(name)` рядом с ним отвечает на другой вопрос: таблицы
нет или таблица пустая. True — есть, False — нет, None — судить не по
чему. Живой случай: `policy_alerts` в базе не существует (её должен
заводить ноутбук, которого пока нет), а «Методология» на пустом ответе
говорила «Новых изменений нет — все источники соответствуют текущим
методологиям».

`safe_read(sql) -> (df, причина)` существует потому, что пустой ответ
на страницах означает не «ничего нет», а конкретный совет: «Данных ещё
нет — соберите товары в Матрице». При недоступной базе этот совет
отправляет человека заводить заново почти тысячу существующих пар,
и выглядит всё нормальной работой. Пустой df с причиной `None` — это
«в базе пусто», пустой с причиной — «прочитать не удалось», и второе
страница обязана сказать вслух.

### `services/settings.py`
Настройки приложения из `app_settings` (key/value) с дефолтами:
`model.*`, `provider.*`, `limit.title`, `limit.highlights`,
`threshold.min_reviews`, `threshold.min_images`, `threshold.rating_*`.
Пороги читаются через `get_int`/`get_float` с фолбэком на
[config.py](../config.py). Кэш 120 c, `save_setting()` чистит кэш.
Таблицы: `app_settings`.

### `services/ai.py`
Единый слой вызова ИИ. Страницы не знают провайдера: выбор задаётся
`provider.<task>` / `model.<task>` в `app_settings`. Задачи: `title_split`,
`photo_audit`, `agents`. Поддержаны Gemini и Anthropic, вход — промпт +
опционально список URL изображений, выход — распарсенный JSON или `None`
(ошибка уже показана в UI).

Постоянная часть промпта передаётся отдельным аргументом `system`: у
Anthropic она уходит блоком с `cache_control: ephemeral` и при партии
читается из кэша, у Gemini — в `systemInstruction`. Кэш там — совпадение
ПРЕФИКСА (порядок `tools` → `system` → `messages`), поэтому всё
меняющееся от товара к товару обязано лежать в `messages`, иначе
кэшировать нечего. Проверять надо не по метке, а по расходу:
`usage_totals()` копит `cache_read_input_tokens` и показывается на
Синтезе после партии.
Таблиц не читает (только `app_settings` через `services.settings`).

### `services/economics.py`
Экономика ASIN за 30 дней: выручка, сессии, конверсия, buy box, шаблон
доставки. Плюс `RULE_RISK` — прозрачные коэффициенты «доля выручки под риском»
по каждому типу боли, и форматтеры денег/конверсии. Нужен, чтобы приоритет
шёл по деньгам, а не только по severity.
Таблицы: `asin_economics`.

### `services/title_rules.py` — правила тайтла кодом (20.10.2026)
Один модуль на всех, кто проверяет тайтл: Синтез, будущий «Генератор текстов
(пилот)» и правило Диагноза. Чистый — без Streamlit и базы, чтобы его взяли и
задача Databricks, и ноутбук сборщика.

- **Общие проверки** перенесены из `pages/synthesis.py` и `services/seo.py`
  без изменения поведения: запрещённые символы, повторы слов, обрезка по
  границе слова, лимиты, `phrase_present` и `keeps_all`. Синтез только
  подставляет лимиты из настроек. Прежние реализации лежат эталоном в
  `test_title_rules.py` и сверяются на наборе строк.
- **Правила пилота** — `check(title, highlights, kind=, model=, rules=Ruleset(...))`
  возвращает коды нарушений:
  - длина;
  - символы (вертикальная черта запрещена, разделитель — запятая);
  - повторы;
  - 220V;
  - вольтаж у инструмента — у аккумуляторов и зарядок можно (`kind`);
  - формат единиц «2000W, 60Nm, Ø230mm, 6600rpm»;
  - бренд;
  - префикс Highlights «Model <модель>: ».
- **Подтверждено владельцем 21.10.2026 по Seller Central ES**
  (GYTR6SYGFA5E3EQC):
  - тайтл ≤ 75 знаков с пробелами, все не-медиа категории. Это константа
    `TITLE_LIMIT`, параметром не меняется;
  - запрещены `! $ ? _ { } ^ ¬ ¦`;
  - слово не больше двух раз, бренд тоже считается.
- **Бренд первым — `brand_position="start"` по умолчанию** (рекомендация
  Amazon, решение владельца 21.10). Регистр — «DNIPRO-M». Остаётся помнить,
  что Amazon на .es однажды вырезал бренд из начала тайтла (29.08.2026).
  Другие позиции — параметром; «бренда быть не должно» (`absent`) ищет его в
  любом регистре.
- **Разделитель — запятая**, параметр `separator` работает. « - », « / », «;»
  между частями тайтла — нарушение, вертикальная черта запрещена всегда.
  Между двумя величинами « - », « – » и « / » — диапазон или размер в
  характеристиках, это можно (решение 21.10). Примеры: «0 - 1700rpm»,
  «Ø230mm / 22,23mm», «6 - 8 mm», две скорости «0 - 450 / 0 - 1700rpm».
  Величина — целым словом `[Ø]число[единица]`. Единицы диапазона шире шаблона
  («0 - 45°», «0 - 4800bpm», «0 - 3000spm»), скобки и точка вокруг не мешают
  («(0 - 1700rpm)»). Поэтому код модели
  («DGA-201M - 125mm»), «2x Baterías», «60Nm - 2 Baterías» и разные единицы
  («2400W - 230mm») — граница частей, нарушение. Ограничение: «2 en 1 - 500W»
  читается как диапазон, по тексту его не отличить.
- **Вольтаж инструмента — нарушение только в тайтле** (`tool_voltage_in`,
  решение 21.10). В Highlights совместимость «compatible con baterías 20V»
  можно.
- Числа проверяются и сразу после «Ø» («Ø230 mm», «Ø230MM»), и после запятой
  без пробела. Регулярное выражение с флагом без учёта регистра считает «Ø»
  буквой вместе с «ø» — это поймал проверяющий #143.
- Тысячи через точку и запятую («10.000rpm») — нарушение. Через пробел — не
  проверяются намеренно: «1 500W» не отличить от «2 en 1 500W» или
  «Pack 2 100W».

### `services/product_specs.py` — характеристики товара для тайтла (21.10.2026)
Шаг 2 пилота «Генератор текстов»: характеристики из атрибутов каталога (с проверкой
единицы) и текста последнего удачного снапшота, у каждого значения источник,
расхождения — `conflicts`, недостающее — `missing`. Тип — по первому слову тайтла;
«Atornillador de Impacto» — свой тип, ударный гайковёрт (21.10.2026).
Подробно и открытые вопросы к таблице типов — [docs/product-specs.md](product-specs.md).

### `services/seo.py`
Поисковый вес фраз и Coverage Score. Четыре типа фраз: `must_keep` (есть
покупки), `preferred` (есть клики), `compress` (только показы), `forbid`
(чужой бренд или нерелевантный запрос). Тип определяется фактами SQP без
участия ИИ; вес = покупки×200 + клики×10 + показы×0.05 + volume×0.001.
Coverage считается кодом: доля сохранённого веса от общего (кроме forbid).
Также — безопасные сжатия (`1500 mAh` → `1.5 Ah`, `milímetros` → `mm`).
Ключи по ТИПУ товара для пилота — `build_type_keyword_table(asins, …)`.
Источник — SQP со всех наших ASIN того же типа: объём — максимум, показы,
клики и покупки — суммой, `asins` — сколько наших товаров видели запрос.
Разбор тот же `guess_tier`, чужие бренды уходят в forbid (решение
20.10.2026).
Таблицы: `sqp_reports` (чтение), `protected_keywords` (запись ручных правок).

### `services/search.py`
Поисковая сводка для витрины: за 4 недели — сколько запросов, суммарный
спрос, доля показов, CTR, покупки. Одна строка на товар, в отличие от
`seo.py` с пофразовой разметкой (обе читают `sqp_reports`). CTR судится
только при `MIN_IMPRESSIONS_FOR_CTR` = 100 показов и выше: у молодого
листинга 3 клика из 12 показов — шум, а не 25% CTR; порог «кликают» —
`threshold.min_ctr` (по умолчанию 0.3%, из практики Amazon: ниже при
заметных показах карточка не убеждает), правится на странице «Методология».
Таблицы: `sqp_reports`.

### `services/attributes.py`
Товар со стороны каталога Amazon: тип товара, browse node, заполненность
атрибутов, `generic_keyword`, буллеты, описание. Пустые атрибуты не видны
глазом на листинге, но выбрасывают товар из фильтров покупателя, а пустой
`generic_keyword` — из выдачи по синонимам; это боли `few_attributes`
и `empty_keywords`. `fill_state` даёт цвет и подпись «12/27»
(`FILL_OK` = 0.85, `FILL_WARN` = 0.5), `missing_critical` — переведённый
список пробелов по важности.
Таблицы: `listing_attributes`.

### `services/serp.py`
Превью выдачи и читаемость тайтла. Считает две стороны: человеческую
(видимая часть на мобиле 60 / десктопе 110 символов, зона первого взгляда 30,
якоря-цифры, чанки, длинное слово) и машинную (пары «атрибут — значение»,
модель, число извлекаемых фактов). Рендерит карточки превью и сравнение
с конкурентами.
Таблицы: `product_matrix`, `listing_snapshots`.

### `services/worklog.py`
След работы по товару: черновики сплита, принятые правки, грейды фото и A+ —
одной картой `(asin, marketplace) → dict`. Даёт HTML-значки для строк
в Матрице и Каталоге.
Таблицы: `synthesis_drafts`, `synthesis_changes`, `photo_analysis`.

### `services/flatfile.py` и `services/flatfile_template.py`
Выгрузка принятых правок в загружаемый файл Amazon. `flatfile_template`
разбирает эталон (вкладка «Plantilla», строки 1–6 служебные, данные с 7-й),
хранит его в `flatfile_templates` со срезанными строками данных и собирает
готовый файл ХИРУРГИЕЙ ПО ZIP: подменяется ровно один XML листа, остальные
42 части архива копируются байт в байт. Пересохранение через openpyxl не
годится — теряются settings первой строки, выпадающие списки и картинки.
`flatfile` раскладывает строки по шаблонам (один шаблон покрывает 30 типов
товара из 60, диапазоны не пересекаются), даёт CSV для человека и список
непопавших строк с причиной.
Таблицы: `synthesis_changes`, `flatfile_templates`, `listing_attributes`,
`catalog_source`, `listing_issues`, `product_matrix`.

### `services/spapi.py`
Прямая отправка принятого тайтла в Amazon (`PATCH /listings/2021-08-01`).
ЕДИНСТВЕННОЕ место, которое пишет в живые листинги клиента, поэтому
модуль ничего не решает сам: диалог подтверждения и защита от повтора
живут на странице, сюда приходит уже подтверждённая ОДНА позиция.
`marketplace_id` и `language_tag` берутся из машинного имени `item_name`
в загруженном шаблоне, а не из таблицы в коде: угаданный идентификатор
рынка означает запись в чужую страну. Политика Amazon с 27.07.2026 —
тайтл сверх 75 не отправляется вовсе, Item Highlights уходят только
вместе с укладывающимся тайтлом. Журнал пишется и при успехе, и при
отказе. `check_connection()` проверяет связь до первой отправки: самый
лёгкий эндпоинт `marketplaceParticipations` проходит весь путь целиком
(refresh token → access token → подписанный запрос), и о сломанной
авторизации узнаём в Настройках, а не на живом товаре.
Таблицы: `listing_push_log` (запись и чтение).

### `services/history.py`
История по товару из трёх таблиц разом: отправки (`listing_push_log`),
принятые правки (`synthesis_changes`) и число генераций
(`synthesis_drafts`), разложенное по интервалам между приёмками —
«сколько заходов понадобилось». Новых полей не требует. Слова
«отклонено» не использует: отказ нигде не сохраняется, и
сгенерированное, не ставшее правкой, отклонённым не было.
Таблицы: `listing_push_log`, `synthesis_changes`, `synthesis_drafts`.

### `services/figma.py`
Чтение макетов и разбор структуры файла. Страница файла = язык
(`UK/US` — источник, `DE/ES/IT/FR` — цели; чужие страницы вроде `Gazi`
и `UK/US (OLD)` пропускаются с отчётом).

**Товар определяется именем ФРЕЙМА: `B0G4S9SJ3M.PT01`.** Разведка
08.09 по живому файлу показала, что «секций» в нём нет вовсе: на
странице лежат подписи (обычный текст) и фреймы макетов, а текст —
внутри фреймов на глубине трёх-четырёх вложений. Прежний разбор
принимал подпись за контейнер, и у каждого товара выходил ровно один
«слой», текст которого равнялся имени подписи.

Подписи дают только SKU и человеческое название, и разбираются
по ПРИЗНАКАМ, а не по шаблону строки: их пишут люди, и на одной
странице UK/US их восемь вариантов — с типом и без, через пробел
и через подчёркивание, SKU перед ASIN и после, иногда SKU нет вовсе.
Строгий шаблон понимал один вариант из восьми и терял 1056 узлов.

**`slot` — «имя фрейма плюс путь в дереве» — то, чем строка одного
языка связывается со строкой другого.** Структура макета на языковых
страницах совпадает точно: английское «Battery Capacity» и немецкое
«Batteriekapazität» лежат в одном месте `PT01#0.1.2`, а id узлов
у них разные. Отсюда же берётся глоссарий: пара нашлась — значит
дизайнер уже перевёл эту строку.

**Опечатки в именах фреймов разбираются, но называются.** В файле
есть `BB0GJMT58WT.MAIN`, `BB0FXY75N5G.MAIN`, `BB0DG616BXX.MAIN` —
лишняя `B` перед ASIN. Строгий шаблон терял у этих товаров фрейм
`.MAIN`, то есть ГЛАВНОЕ изображение: в списке и превью показывался
бы слайд `PT01` вместо фото. Текста в `.MAIN` нет, поэтому перевод
не страдал — страдало то, по чему товар узнают. Перед ASIN
допускаются одна-две лишние буквы, не больше, а сами имена идут
в отчёт (`typo_frames`) и на экран: чинить их надо в Figma, иначе
поправка останется в коде навсегда.

**Модули A+ (`carousel …`) привязываются ПОДПИСЯМИ, а нумеруются
ПОЗИЦИЕЙ.** ASIN в их имени нет, «carousel 2.2» есть у многих
товаров, и до 17.09 они были отложены целиком — 564 фрейма, половина
макетов. Разведка по живому файлу (один запрос, документ в кэше)
показала, что работает: над каждой группой модулей на холсте стоит
подпись товара («A+ Premium Content_<ASIN>» или подпись без типа),
и правило «ближайшая подпись выше, центр фрейма внутри её ширины;
подпись без типа берёт только то, что лежит НИЖЕ слайдов товара»
привязывает 564 из 564, сирот ноль (`attach_aplus`). Имя фрейма
для `slot` при этом СИНТЕТИЧЕСКОЕ: `B0G4S9SJ3M.A+d05` — ASIN,
вариант по ширине (d = 2718 десктоп, m = 1398 мобайл), порядковый
номер по рядам сверху вниз и слева направо. Настоящие имена между
языками расходятся (у одного товара 12 из 18, у B0H26WGJFS 2 из 10),
позиция — нет: по ней сходятся 492 из 498 языковых модулей.
Настоящее имя («carousel 3.1») остаётся в `frame_name` для человека.
Порог ряда — `floor(x + 0.5)`, а не `round()`: у Python он
банковский, у JavaScript вверх, и на границе сотни плагин разошёлся
бы с разбором; тест ловит именно эту мутацию. Модуль без подписи
(`aplus_orphans`) и два фрейма с одним именем на одной странице
(`dupe_frames`, девять на UK/US) идут в отчёт и на экран: чинятся
они только в Figma, файл дизайнера код не трогает.

Картинки не трогаются вовсе: они вставлены с отрицательными
координатами и обрезаны рамкой, любое вмешательство сдвинет
кадрирование.

**После 429 на рендере в Figma не ходим до конца срока (27.09).**
Рендер `/v1/images` — отдельный запрос от чтения файла, и лимит
у него свой. После перехода на токен design@ чтение шло (200), а
рендер отвечал 429 «Rate limit exceeded» с `Retry-After: 266304` —
и картинки пропали целиком, а список молчал по задумке. Хуже того,
каждый показ списка просил ссылку на каждую из 21 миниатюры,
редактор — на каждый из 27 слайдов, и каждый запрос получал тот же
429. Теперь `node_image` после 429 ставит паузу на процесс (квота
одна на все сессии) и до её конца отдаёт ту же причину без запроса
(`images_paused()`); в причине — срок словами и `X-Figma-Rate-Limit-
Type`, если Figma его прислала. Причина видна: в редакторе — плашкой
над слайдами (у слайда коротко «картинки макета нет»), в списке —
одной строкой над ним; у отдельной миниатюры по-прежнему молчание.

**Retry-After — всегда секунды; тип «low» — место View, а не пауза.**
Здесь было правило «больше суток — миллисекунды» (306325 читалось
как пять минут). Оно было неверным: 27.09 сверка показала, что
значение убывает ровно на секунды (за 32 минуты — на 1924), а
266304 — это ~74 часа до сброса МЕСЯЧНОЙ квоты. Токен design@ стоит
на месте View: 6 запросов в месяц на Tier 1 (чтение файла и рендер
вместе), заголовок `X-Figma-Rate-Limit-Type: low`. При типе low
экран называет причину — «место View — 6 запросов в месяц, нужно
место Dev или Full» — а не «подождите», и кнопка «Перечитать»
тоже (`loc.rate_low`). `rate_limit_reason()` — одно место для обеих
дорог (чтение и рендер).

**Рендеры хранятся навсегда — `figma_renders` (миграция 2026-09-27).**
Отрендерили раз — легло в базу, дальше показываем оттуда без
запроса к Figma; суточный кэш в памяти терялся при каждом ребуте и
тратил квоту на то, что не менялось. Перерисовывается узел, только
когда изменился ОН: `node_hash` — отпечаток поддерева из документа,
который и так читается при «Перечитать» (ноль лишних запросов),
без имён и с координатами относительно самого узла — сдвиг фрейма
по холсту и переименование картинку не меняют. Не `lastModified`
файла: он меняется от любой правки и перерисовывал бы все картинки
разом. Недостающие рендерятся ПАЧКОЙ (`node_images`, до 50 узлов на
запрос): все слайды товара — один. Список рендеров не просит
вовсе — у него фото Amazon, см. выше. Без миграции код работает по-старому и называет файл миграции
над списком.

`char_limit()` считает предел символов по ширине слоя и кеглю
(`AVG_CHAR_RATIO` = 0.52 — средняя ширина знака гротеска как доля
кегля), с учётом числа строк. Точным он быть не может, поэтому на
экране стоит подпись про расчёт, а разбор делает самопроверку:
английский текст УЖЕ стоит в макете, и если расчёт говорит, что он
не влезает на заметной доле слоёв, занижен коэффициент — страница
скажет об этом сама.
Таблиц не читает.

### `services/passport_intake.py` и `services/passport_actions.py` — этап 3а
Приём исходных материалов и проверки до запроса. Не пишут в базу и не
зависят от того, где живёт `product_root`: копия ложится в `ArtifactStore`
с методами `put` и `get`, а пока есть только хранилище в памяти для тестов.

**Приём — по политике канона и утверждённому профилю (LS-CFG-001/002).**
Профиль проверяется по подписи: SHA считается от компактного JSON в порядке
полей файла, без самого поля SHA. Проверено на всех четырёх профилях канона:
сортировка ключей даёт другой хэш. Правка предела без новой подписи —
`INTAKE_POLICY_NOT_CONFIGURED`, и приём не начинается. Порядок проверок —
из политики, и он важен:

- выход за выбранный корень и ссылки отвергаются ДО чтения содержимого;
- тип проверяется и по расширению, и по байтам — PDF под именем .png даёт
  `TYPE_MISMATCH`, а не тихий приём;
- длительность видео читается из заголовка (MP4/MOV — `mvhd`, WebM — EBML);
  не прочиталась — файл не принят: проверить предел нечем;
- пределы на объект — у объекта, пределы на снимок (100 файлов, 5 ГиБ) —
  у всего набора разом, `REJECTED_POLICY`;
- `ACCEPTED` бывает только после копии, хэша и повторного чтения.

Граничная матрица канона (13 случаев) исполняется против `limit_reason()`.

**ZIP — выбранная папка, а не источник.** Владелец Listing Suite решил,
что материалы можно грузить архивом, а канон архив как источник запрещает
(`.zip` нет в списке, граничный случай `ARCHIVE-NOT-ALLOWED`). Поэтому архив
разворачивается, каждый файл внутри проверяется отдельно, а сам архив не
регистрируется. Архив внутри архива — `TYPE_NOT_ALLOWED`.

**Проверки до запроса — порядок Handoff:** схема → полномочия → точный SKU
→ текущий Паспорт (id, версия, SHA) → состав → идемпотентность →
блокировка. Канонический профиль полномочий стоит в `BINDING_REQUIRED`,
поэтому сейчас любой запрос получает `AUTHORITY_PROFILE_NOT_ACTIVE`. Это
fail-closed по контракту, а не недоделка. Роль из интерфейса
(`actor_authority`) доказательством не является. Хэш запроса считается от
сериализации с ключами по алфавиту: один запрос — один хэш, без ложного
`IDEMPOTENCY_KEY_CONFLICT`.

На вкладке «Создание» поле материалов показывает пооб'єктную проверку до
запуска: «пройдёт приём», а не «принят» — копии пока не делаются. Рядом —
контроль перед запуском по пунктам ТЗ 10.3.4. Вместо «готово» там прямо
сказано, чего не хватает: места для папки товара и привязки полномочий.

### `services/passport_answers.py` — ответ Верификатору, этап 4а
Текст и решение по конфликту, без вложений. Документ или ссылка как
доказательство — исходный материал, его копия ложится в `product_root`, а
он ещё не решён. Поэтому вопрос, требующий документа, сейчас не отправить,
и это сказано словами (`pp.ans.err.EVIDENCE_NEEDS_STORAGE`). Запись —
только при включённом флаге `listing_suite.verifier_answers`, флаг выключен.

Правила:

- **Ответ неизменяем.** Каждая отправка — новая строка `passport_answers` с
  ID `A-<question_id>-<NNN>` по шаблону 06E. Исправление — новая версия со
  ссылкой на прежнюю. Прежнюю не перезаписывают: держит триггер базы.
- **Двойное нажатие — один ответ.** Ключ идемпотентности считается от
  вопроса, версии, на которую отвечают, автора и содержания. Запись идёт с
  `ON CONFLICT DO NOTHING` и повторным чтением по ключу.
- **Статус вопроса экран не трогает.** Переходы фиксирует Собиратель (06E).
  «Ожидает проверки» выводится из факта непроверенной последней версии в
  `passport.user_state`, иначе только что отправленный ответ снова звал бы
  «Ответить». Проверенный, но не применённый — тоже не «решён».
- **Решение по конфликту.** Только четыре значения ТЗ 11.4.3 и только у
  владельца данных (`PRODUCT_OWNER`, `PASSPORT_ADMIN`). Без полномочий можно
  передать пояснение, но не решение.
- **Устаревший вопрос закрыт для ответа.** Снимок Паспорта, по которому
  задан вопрос, берётся из `run_state.pinned_product_truth` запуска. SHA
  текущего Паспорта другой — отправка закрыта до сверки.
- **Полномочия — в момент нажатия.** Перед записью данные перечитываются
  заново: вопрос мог закрыться, Паспорт — смениться.

Формы DOCX и XLSX сюда не входят. Внешнюю форму материализует Верификатор,
со сверкой смысла каждого вопроса (06E «Смысловая сохранность»): форма,
собранная экраном в обход этой сверки, подменила бы его работу. Вернувшаяся
заполненная форма регистрируется как исходный материал — это снова
хранилище.

### `services/graph_*.py` — ядро движка графа AI Design (15.10.2026)
Общее для Паспорта и будущего «Контента»: граф один, запуск «Контента»
продолжается в нём же. Перенос эталонных скриптов канона
(`canon/ai_design_conveyor/10_Runtime_Registry/*.ps1`) на Python, без вызовов
модели и без файлового хранилища. Streamlit модули не тянут: их возьмёт задача
Databricks как есть.

| модуль | что делает | эталон |
|---|---|---|
| `graph_canon` | реестры из снимка со сверкой SHA по манифесту, хэш состояния, схемы канона | — |
| `graph_gates` | входы проверок рёбер и вердикт по ребру | `New-AIDesignGateInputs`, `Invoke-AIDesignGateEvaluation` |
| `graph_router` | одно годное ребро — выбор; два — человек; ноль — блок с причиной | `New-AIDesignRouterDecision` |
| `graph_budget` | ledger и квитанция бюджета | `Resolve-AIDesignTerminationBudget` |
| `graph_writer` | начальное состояние и запись перехода | `New-AIDesignControlledRunState`, `Invoke-AIDesignStateTransition` |
| `graph_engine` | один шаг: входы → проверки → решение → бюджет → запись | `Invoke-AIDesignShadowRun` |
| `graph_store` | `ai_runs` и `ai_run_events`, шаг — одна транзакция под `FOR UPDATE` | — |

**Условие ребра — грамматика из четырёх атомов, а не `eval`.** Так велит
контракт маршрутизатора. Сравнение строже эталона: булево не равно числу,
строка сравнивается с регистром. PowerShell считает `$true -eq 1` истиной;
у нас расхождение типов может только закрыть ребро, но не открыть.

**Факт либо доказан, либо UNRESOLVED.** Из состояния выводятся ровно девять
фактов, как у эталона. Ещё 74 факта того же вида закрытой функции не имеют,
поэтому их рёбра стоят с `GUARD_UNRESOLVED`, пока функция не появится.
Внешний факт принимается только со сверкой SHA источника. Сверяет вызывающий:
своего хранилища у ядра нет.

**Где перенос сознательно расходится со скриптом — в пользу контракта:**

- Запись перехода требует квитанцию бюджета текущей ревизии ledger
  (правила 13–16). Эталон бюджет не вызывает вовсе.
- Применённое ребро снова доступно, когда его источник активен (правило 8).
  У эталона ребро переделки срабатывает раз за запуск.
- Версия графа берётся из файла контракта (2.6), а не из скрипта (2.5).
- Класс события бюджета выводится из класса ребра: RETRY → REWORK,
  RESUME → CHECKPOINT_RESUME. В каноне сопоставления нет; выбрано то, что
  списывает больше.

Все четыре — в `canon/REFERENCE_DRIFT.md` (раздел 4) и ушли владельцу.

**Хранение.** Ledger отдельной таблицы не имеет. Событие 1 — создание
запуска с начальным ledger, каждое следующее — применённый переход или
исчерпание бюджета, вместе с решением маршрутизатора и новой ревизией
ledger. Решения без перехода (`RUN_BLOCKED` и прочие) событием не
становятся: маршрутизатор состояние не меняет. Шаг по устаревшему снимку
отвергается (`expected_state_sha256`).

**Чего ядро пока не умеет, и почему.** Запуск первичного создания: схема
run_state требует SHA существующего Паспорта, вопрос у владельца. Ребро E183:
условие `факт == факт` вне грамматики, эталон тоже падает. Узлы не
исполняются: адаптеры узлов (вызов модели, приём материалов) — следующие
этапы, им нужны `product_root` и ключи провайдеров.
