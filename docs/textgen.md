# «Генератор текстов (пилот)» — страница

Код — `pages/textgen.py`, тест — `tests/test_textgen_page.py`, роль — AGENTS.md,
раздел «Вход через Google и роли». Задача — TASKS.md, T-20.

## Роль

**Роль пилота «Генератор текстов» — `textgen_pilot` (с 21.10.2026).** Решение
владельца: Ярослав — не администратор. Роль видит ОДНУ страницу, `ls.page.textgen`,
и ни одного действия; сам генератор видят только она и администратор. Прочие роли
видят остальные страницы, как раньше. В базе Кабинета роль заводит
`migrations/kabinet/2026-10-21_ls_textgen_role.sql`: оба CHECK, строки матрицы и
назначение Ярославу по почте. Почта в файле не подставлена, и пока это так, файл
отказывается выполняться. Применяет владелец. Лежит не в корне `migrations/`,
потому что это не миграция `listing_data`. Две оговорки:

- экран «Доступ» роль не знает, пока не поправлен `access_screen.py` у источника,
  в Кабинете. До этого строку Ярослава на экране «Доступ» не редактировать;
- в режиме 2 (раскатка) права не действуют, генератор видят все.
- сверка Кабинета `scratchpad/smoke_ls_auth.py` ждёт ровно 4 строки `ls.admin`.
  После SQL их пять (пятая — `textgen_pilot`, false), и сверку надо поправить
  в Кабинете вместе с `access_screen.py`. До SQL она тоже красная: нет строки
  `ls.page.textgen`;
- тестовый вход QA генератора не видит — решение владельца 21.10.2026
  (`auth.QA_PAGE_ACTIONS`): все страницы, кроме этой.

## Страница

Пять пилотных товаров ES (TASKS.md, T-20). Видят администратор и роль
`textgen_pilot`. Модель не вызывается, в базу и в Amazon ничего не уходит.
Генерация появится, когда придёт документ «Предложения».

Что на странице:

- **Товар.** Тип, модель, питание и нынешний тайтл с длиной.
- **Характеристики.** У каждого значения назван источник: атрибут каталога,
  снапшот, Highlights, тайтл или набор. Ниже — части для тайтла по таблице
  типа и чего не хватает. Расхождение карточки называется вслух: у DHR-202BC
  4 Ah в атрибуте против 6Ah в наборе. Значение молча не выбирается.
- **Ключи по типу.** Запросы со всех наших товаров того же типа, чужие бренды
  и нерелевантное — «не брать» (`seo.guess_tier`). Отметка «есть в тексте»
  считается по введённому.
- **Тайтл и Highlights руками.** Счётчики длины и живая проверка
  `title_rules.check()`. На экране ровно её нарушения — своей логики
  проверки у страницы нет, иначе экран разошёлся бы с будущей генерацией.
  Если кода модели нет ни в данных, ни в тайтле, префикс Highlights
  «Model …: » не проверить, и экран говорит это отдельной строкой: «нарушений
  нет» без оговорки выдавало бы непроверенное за проверенное.

Кешируется только удачное чтение. Сбой поднимается исключением, а исключения
`st.cache_data` не запоминает. Иначе разовый сбой базы висел бы на экране
весь срок кеша. Сбой чтения — ошибка с причиной, а не «характеристик нет»;
сбой SQP — ошибка, а не «данных поиска нет».

Данные — из `services/product_specs.py`, `services/seo.py` и
`services/title_rules.py`, без копий.
Читает: `listing_snapshots`, `listing_attributes`, `product_matrix`,
`sqp_reports`. Не пишет ничего.

## Тест

`test_textgen_page.py` — «Генератор текстов (пилот)», каркас без модели. Что
проверяется:

- нарушения на экране — ровно те, что вернул `title_rules.check()`, каждое
  своим кодом;
- вольтаж инструмента: в Highlights не нарушение, в тайтле нарушение;
- расхождение 4 Ah / 6Ah у DHR-202BC названо;
- сбой чтения и сбой SQP — ошибки с причиной, и они не кешируются: база
  ответила — карточка на месте;
- модель не вызывается, страница ничего не пишет;
- колонки — технические имена, ключи всех подписей есть в трёх языках;
- SQL роли для базы Кабинета: роль в обоих CHECK, генератор — ровно ролям из
  кода, всё прочее пилоту закрыто явными строками, без подставленной почты
  файл не выполняется.

Страница прогоняется через AppTest на данных `fixture_pilot.py`. Мутации валят
свои проверки: `kind` всегда «аккумулятор», нет предупреждений о
расхождении, закешированный сбой, CHECK без роли пилота, незакрытый
`ls.admin`, генератор всем.

Права роли пилота — в `test_auth_roles.py`: видит генератор и больше ни одной
страницы, ни одного действия. Это проверяется и по матрице кода, и по матрице
из базы. Прочие роли генератор не видят. Без строки в базе его не видит даже
администратор.

## Хранение контента (решение владельца 21.10.2026)

Своя таблица `content_versions` — миграция `migrations/2026-10-22_content_versions.sql`,
применяет владелец. `synthesis_changes` не подходит:

- там обязателен ASIN, а у нового товара его нет;
- одна строка — пара «тайтл + Highlights», буллеты и описание не ложатся;
- нет версий, автора и ссылки на паспорт;
- её читает выгрузка flat file Синтеза для Amazon.

Устройство:

- строка — одна версия одного поля: title, highlight, bullet_1…5, description;
  ключ — точный SKU (`99601000-B`) и рынок, ASIN не обязателен;
- статусы draft → accepted → sent. «Отправлено» — выгружено и передано Марко,
  отдельной кнопкой; сверка с живым листингом — позже;
- действующая версия поля — последняя по номеру среди accepted и sent.
  Статуса «заменено» нет: какая версия действует, говорит номер;
- паспорт-источник: `passport_id`, версия, SHA и ссылка на строку
  `passport_source_artifacts`. Копия docx — в томе UC,
  `<sku>/<passport_id>/v<версия>/`. Drive пока не заводим.

Что держит база: текст и происхождение неизменяемы, статус только вперёд с
автором и временем каждого шага, удаления нет, номер версии и повтор прогона не
дублируются. Проверено прогоном миграции на PGlite (Postgres в WebAssembly):
каждый запрет срабатывает, разрешённые шаги проходят. Статически заперто
`tests/test_content_versions_sql.py`.

Право на кнопки «Принять» и «Выгрузить» — `ls.textgen.accept`, у администратора
и роли пилота. SQL для базы Кабинета —
`migrations/kabinet/2026-10-22_ls_textgen_accept.sql`, владелец применяет, когда
подключат Алексея. В `auth.py` действие появится вместе с кнопками.

Выгрузка Марко — XLSX и CSV, строка = SKU × рынок, только принятые версии.
Flat file Amazon — позже.

Порядок PR, каждый — по команде владельца: миграция → загрузка паспорта в том
→ кнопки «Принять» и «Выгрузить».
