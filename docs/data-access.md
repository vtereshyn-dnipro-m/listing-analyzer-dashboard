# Подключение к данным — подробно

Перенесено из AGENTS.md 21.10.2026 дословно, раздел «Подключение к данным» (решение владельца: в AGENTS.md — правила и ссылки). Ссылки поправлены под папку `docs/`; содержание не менялось.


`services/db.py::get_conn()` — единственная точка входа для записи,
`get_engine()` — для чтения через pandas. Голое psycopg2-соединение
в `pd.read_sql` не передаётся — pandas на это предупреждает на каждый
вызов. Три режима, определяются автоматически в этом порядке:

1. **Notebook** (ноутбук Databricks): `LISTING_LAKEBASE_ENDPOINT` +
   `databricks.sdk` → OAuth-токен (~1 час).
2. **Dashboard** (Streamlit Cloud): секция `[databricks]` в секретах →
   service principal OAuth.
3. **DSN** (локально): `DATABASE_URL` → `psycopg2.connect(url)`.

`search_path` всегда выставляется в `listing_data, public`, поэтому в SQL имена
таблиц пишутся без префикса схемы.

**Соединения живут в ПУЛЕ, а не открываются на каждый запрос (21.09).**
Одно соединение стоит ~1,6 с: `generate_database_credential` — REST-вызов
в Databricks (~1 с) плюс TLS-рукопожатие с Postgres (~0,6 с). До 21.09
и токен, и соединение брались на КАЖДЫЙ запрос — движок стоял на
`NullPool`. Замер по AppTest с подменённым psycopg2 (сеть не трогается,
считаются вызовы `connect`): первый показ Каталога — 11 физических
соединений, Матрицы — 10, Методологии — 9, Диагноза — 6; по шести
страницам 50 соединений, то есть около 80 секунд только на подключения.
После пула — по одному на страницу, 6 против 50. На Кабинете тот же
класс дал 40 секунд из 56 на первом показе «Справочников».

Как устроено: токен кешируется на `TOKEN_TTL_S` (50 минут при часе
жизни) в `@st.cache_resource` — не `cache_data`, иначе он вылетал бы
на каждом `cache_data.clear()` после записи; физические соединения
держит `QueuePool` SQLAlchemy (`get_engine`), а `get_conn()` выдаёт
соединение ИЗ ПУЛА — `close()` возвращает его туда, а не рвёт.

Прежнее объяснение `NullPool` («соединение из пула переживёт токен»)
было неверно понятым ограничением: пароль Postgres проверяет ТОЛЬКО
при подключении, открытое соединение живёт дальше. Пережить токен
может лишь попытка открыть НОВОЕ — от этого `pool_recycle` (45 минут,
раньше истечения кеша токена) и повтор с принудительно свежим токеном
на отказ авторизации, ровно один.

`get_conn()` возвращает `PooledConnection` — обёртку, а не прокси
SQLAlchemy, из-за одной разницы: у psycopg2 `with conn:` это КОММИТ
без закрытия, и так написаны все записи проекта
(`with conn, conn.cursor() as cur:`, затем `conn.close()`). У прокси
`__exit__` — это `close()`: соединение ушло бы в пул без коммита,
транзакция откатилась бы при возврате, и запись пропала бы МОЛЧА.
Поведение заперто `test_db_pool.py`.

**Правило DDL: миграции идут через Databricks, по команде владельца.** Каждая —
отдельный `.sql` в [migrations/](../migrations/), см. [migrations/README.md](../migrations/README.md).
С 21.10.2026 применяет агент по команде «применяй <имя файла>», под учёткой
владельца (раздел «Автономия»).
Приложение схему не создаёт и не меняет — только `SELECT` и разрешённые
`INSERT`/`UPDATE`.

**Код и миграция едут порознь, и код обязан это переживать.** Мерж
попадает на Cloud раньше, чем `.sql` — в Databricks; 18.09 Каталог
лёг целиком на `SELECT s.buy_box_owner` — «column does not exist».
Страница, читающая НОВУЮ колонку, спрашивает
`services/db.py::missing_columns()` и без колонки работает по старой
схеме, а сверху говорит, какой миграции не хватает и где она лежит.
Тест страницы обязан проверять обе схемы, и фикстура «без миграции»
должна ПАДАТЬ на новой колонке, как падает база, — иначе проверка
не запирает то, что сломалось.

Раньше здесь значилась «единая точка миграций» `ensure_all_schemas()` из
ячейки ноутбука. Она не работала: все три её импорта падали, и четыре
миграции подряд прошли мимо неё. Функция удалена — механизм, который
не работает, но выглядит работающим, хуже отсутствующего.

Секреты читаются через `services.db.cfg(name)`: env → `.streamlit/secrets.toml`
на диске → `st.secrets` → default. Ключи: `SCRAPINGDOG_API_KEY`,
`GEMINI_API_KEY`, `ANTHROPIC_API_KEY`.
