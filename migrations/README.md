# Миграции

Каждый файл — одна миграция, имя `YYYY-MM-DD_что.sql`. Применяются
**через Databricks**, по команде владельца (с 21.10.2026 — агентом под учёткой
владельца, см. «Порядок»): приложение схему не создаёт и не меняет.
`migrations/kabinet/` — SQL для базы Кабинета, его применяет только владелец.

Так сложилось не случайно. Раньше в `services/db.py` жила
`ensure_all_schemas()` — «единая точка миграций» из ячейки ноутбука. Она
не работала: все три её импорта падали, и четыре миграции подряд прошли
мимо неё, отдельными файлами. Функцию убрали: механизм, который не
работает, но выглядит работающим, хуже отсутствующего — он создаёт
ощущение, что схема под контролем.

## Порядок

1. Написать `.sql` в этой папке, с комментарием ЗАЧЕМ таблица или колонка.
2. Применить — по команде владельца «применяй <имя файла>», под его учёткой
   Databricks (с 21.10.2026):
   `python scratchpad/apply_migration.py migrations/<файл>.sql`. Скрипт
   делает предпроверку, применяет файл до `COMMIT`, выполняет проверочные
   запросы из конца файла, а при ошибке откатывает. `--check-only` —
   только предпроверка, без изменений. Удаление данных и любой `DROP` агент
   не делает никогда, кроме одного (владелец, 21.10.2026): пересоздание
   триггера — `DROP TRIGGER IF EXISTS X ON T`, затем `CREATE TRIGGER X … ON T`
   в том же файле до `COMMIT`. Порядок проверяет скрипт: `CREATE` раньше
   `DROP` — отказ.
3. Только потом мержить код, который на неё опирается.
4. Обновить снимок схемы в [../schema/](../schema/) — он и есть то,
   с чем сверяется `test_schema_contract.py`. Пропуск этого шага тест
   не роняет (таблицы из миграций считаются допустимыми), но снимок
   тихо расходится с базой, а именно ради него его и заводили.

Пункт 3 не формальность: код, слитый раньше миграции, падает на живых
пользователях, а не на ревью.
