# Функциональное ТЗ «Listing Suite → Контент → Паспорт SKU»

Статус документа: `APPROVED_FOR_IMPLEMENTATION`  
Версия: `1.0`  
Дата: `2026-10-04`  
Владелец решения: владелец процесса AI Design

## 1. Назначение

Область даёт пользователю единое место для поиска Паспорта точного SKU, запуска его создания или дополнения, взаимодействия с Верификатором и управления сбором медиа через `Image Collection`.

Интерфейс является точкой запуска действий, внесения требуемой информации и получения результатов. Он не имитирует внутренний конвейер, не предлагает пользователю вручную передавать пакеты между агентами и не подменяет Координатора.

## 2. Область применения

Расположение: `Listing Suite → Контент → Паспорт SKU`.

Внутренние вкладки:

1. `Реестр Паспортов` — найти Паспорт и определить следующее доступное действие.
2. `Создание Паспорта` — передать документы и иные немедийные исходные материалы, создать Паспорт либо передать новые данные в существующий Паспорт.
3. `Взаимодействие с Верификатором` — отработать адресные запросы Верификатора: предоставить ответ, документ или решение по конфликту.
4. `Image Collection` — увидеть уже собранные медиаисточники, передать фото/видео/прямые ссылки и запустить первичный либо дополнительный сбор медиа.

Отдельные верхнеуровневые вкладки `Обновления`, `Медиа` и `История` не создаются. Дополнение Паспорта выполняется во вкладке `Создание Паспорта`; сбор и квалификация медиа — во вкладке `Image Collection`; история отображается контекстно внутри Паспорта, вопроса, запуска и collection.

## 3. Порядок проработки ТЗ и визуализаций

1. Всё функциональное ТЗ области и её вкладок ведётся в этом документе.
2. Вкладки прорабатываются и утверждаются последовательно.
3. До утверждения вкладки в документе фиксируется только её название и краткое назначение; неподтверждённые функции не считаются требованиями.
4. Сразу после утверждения функционального раздела вкладки создаётся её визуализация.
5. Утверждённая визуализация добавляется в соответствующий раздел этого документа с номером версии.
6. Если визуализация выявляет противоречие, сначала корректируется ТЗ, затем выпускается новая версия визуализации.

### 3.1. Приоритет ТЗ над утверждёнными эскизами

Эскиз фиксирует согласованную композицию и визуальную систему, но не заменяет machine-readable контракт. При расхождении подписи, статуса, ID или действия реализация следует этому ТЗ и действующим контрактам конвейера.

После контрактного аудита `2026-10-03` для реализации обязательны следующие текстовые коррекции, даже если на утверждённой PNG-версии сохранён прежний пример:

- на всех экранах используется название `Взаимодействие с Верификатором` вместо `Вопросы и ответы` или `Запросы Верификатора`;
- `BLOCKED / Заблокирован` показывается только по active `BLK-<RUN>-<NNN>`;
- Question `SENT` без block record показывает `NOT_READY / В работе` и отдельное `Требуется ответ`;
- пользовательская кнопка `Синхронизировать` отсутствует;
- question ID имеет формат `Q-<RUN>-<NNN>`;
- `Решение конфликта` является типом запроса, а не его состоянием;
- placeholder ответа: `Введите ответ на запрос Верификатора`;
- результаты `source_evidence_delta` используют только коды 00A.

Эти изменения не меняют утверждённую компоновку экранов и не требуют изменения инструкций агентов.

## 4. Общие входные данные и контракт

Для любой операции требуется точный `sku_id`. Название, модель, ASIN, EAN и другие идентификаторы могут использоваться для поиска, но не заменяют подтверждённый SKU при запуске.

Для существующего Паспорта интерфейс получает как минимум:

- `sku_id` и версию товара;
- `passport_id`, путь, `passport_version`, SHA-256;
- состояние Паспорта;
- количество активных вопросов, ограничений и блокеров;
- допустимое следующее пользовательское действие;
- ссылку на папку материалов в контексте текущего пользователя.

Нормативные зависимости:

- [Контракт передач Паспорта SKU](00A_Контракт_передач_Паспорта_SKU.md);
- [Агент-координатор](00_Агент_координатор_конвейера_Паспорта_SKU.md);
- [Реестр вопросов и ответов](06E_MVP_Реестр_вопросов_и_ответов.md);
- [Функциональное ТЗ Паспорта SKU](Listing_Suite_ТЗ_Синтез_Паспорт_SKU_v01.md).

## 5. Общие правила выполнения

1. Для точного SKU существует один логический и один физический Паспорт; версии ведутся внутри него.
2. Просмотр Паспорта в кабинете не даёт прямого редактирования Product Truth.
3. Внутренние переходы `Координатор → Собиратель → Аудитор → Верификатор` не отображаются как пользовательские кнопки.
4. Пользователь видит действие только тогда, когда для него определены вход, агентский маршрут, результат и состояние ошибки.
5. Состояние генерации или проверки креативов не изменяет автоматически состояние Паспорта.
6. Переход в папку материалов выполняется с текущей учётной записью; права определяются внешней политикой доступа.
7. Генерация контента и публикация не разрешаются фактом наличия Паспорта.

### 5.1. Функция «Передать новые данные»

Функция `Передать новые данные` является отдельным ограниченным сценарием для существующего Паспорта. Она не создаёт новый Паспорт, не запускает полный повторный сбор и не позволяет напрямую редактировать Product Truth.

Пользователь передаёт новые файлы, ссылки или папку материалов для точного SKU. Интерфейс запускает Координатора с route `source_evidence_delta`; дальнейшее сравнение, проверка и применение выполняют назначенные агенты по контракту.

Функция доступна только когда:

- точный SKU подтверждён;
- найден один актуальный канонический Паспорт;
- версия и SHA Паспорта актуальны;
- добавлен хотя бы один доступный исходный материал;
- отсутствует другой активный delta-run для того же Паспорта и scope.

Свободная команда изменить конкретное значение без source artifact не является этим сценарием.

## 6. Роли и ответственность

- Пользователь выбирает точный товар, передаёт разрешённый вход и отвечает на адресные вопросы.
- Координатор определяет текущий этап и запускает только разрешённого агента.
- Собиратель создаёт и изменяет единый Паспорт.
- Аудитор выполняет независимую проверку в рамках контракта.
- Верификатор оценивает evidence, формирует вопросы и решения, но не редактирует Паспорт.
- Владелец процесса утверждает пользовательские сценарии и контрактные изменения.

## 7. Состояния Паспорта

- `NOT_READY` — нужны внутренние действия или проверка.
- `BLOCKED` — требуется определённое внешнее условие возобновления.
- `READY_WITH_LIMITATIONS` — Паспорт применим только с утверждёнными ограничениями.
- `READY` — выполнены Acceptance checks заявленного scope.

Состояния вопросов, запусков, источников и креативов показываются отдельно и не подменяют состояние Паспорта.

## 8. Навигация и сохранение контекста

После выбора строки в `Реестре Паспортов` область сохраняет `sku_id` и версию товара при переходах между внутренними вкладками. В заголовке каждой вкладки отображаются выбранные SKU, название/модель и состояние Паспорта. Смена SKU требует явного выбора; скрытое переключение запрещено.

Если действие открывается из строки Реестра, пользователь попадает сразу в нужную вкладку и нужный объект: вопрос, ограничение, блокер, запуск или медиа-задачу.

## 9. Вкладка «Реестр Паспортов»

Статус раздела: `APPROVED`  
Статус визуализации: `APPROVED`

### 9.1. Назначение

Вкладка помогает найти товар, понять, существует ли его Паспорт, увидеть актуальное состояние и перейти к одному допустимому следующему действию.

`Реестр Паспортов` не является редактором Паспорта и не является визуализацией внутренних этапов конвейера.

### 9.2. Основной пользовательский сценарий

1. Пользователь вводит SKU, название, модель, ASIN или EAN.
2. Система показывает совпадения и признаки, позволяющие выбрать точный товар.
3. Пользователь выбирает одну строку.
4. Система показывает краткую карточку выбранного SKU и одно основное следующее действие.
5. Действие открывает соответствующую вкладку с сохранённым контекстом товара.

### 9.3. Поиск и фильтры

- единое поле поиска с подсказкой `SKU, название, модель, ASIN или EAN`;
- фильтр состояния Паспорта;
- фильтр наличия активного действия пользователя;
- сброс фильтров.

Поисковый результат по названию или внешнему идентификатору не считается подтверждением SKU.

### 9.4. Таблица результатов

| Колонка | Содержание |
|---|---|
| Товар | название и модель |
| SKU | точный `sku_id` |
| Версия товара | конфигурация/версия отдельно от SKU |
| Статус Паспорта | канонический статус либо `Паспорт отсутствует` |
| Версия Паспорта | текущая внутренняя версия |
| Вопросы | количество активных вопросов, требующих действия пользователя |
| Ограничения/блокеры | количество и критичный индикатор |
| Последнее изменение | дата и тип последнего принятого события |
| Следующее действие | одна контекстная кнопка |

Колонка `Новые материалы` не используется: без утверждённого пользовательского сценария она создаёт ложное обещание обработки произвольных данных.

### 9.5. Карточка выбранного SKU

Карточка показывает:

- SKU, название, модель/версию;
- состояние и версию Паспорта;
- дату последнего подтверждённого изменения;
- активные ограничения и блокер с условием возобновления;
- вторичные переходы `Открыть Паспорт` и `Открыть папку материалов`;
- одно основное следующее действие.

Паспорт открывается в read-only режиме. Папка материалов открывается с текущей учётной записью.

### 9.6. Модель статусов в Реестре

Реестр не сводит разные состояния к одному цветному ярлыку. Для каждой строки отдельно определяются:

1. наличие Паспорта;
2. состояние Паспорта;
3. необходимость действия пользователя;
4. актуальность и техническая достоверность показанных данных.

#### 9.6.1. Состояния Паспорта

| Machine-readable status | Название в интерфейсе | Значение для пользователя | Основное отображение | Что разрешено |
|---|---|---|---|---|
| `READY` | `Готов` | Acceptance checks заявленного scope выполнены; обязательных открытых gaps и активных блокеров нет | зелёный status chip | открыть Паспорт и использовать его в разрешённых downstream-сценариях |
| `READY_WITH_LIMITATIONS` | `Готов с ограничениями` | Паспорт применим, но только с явно утверждёнными optional limitations | жёлтый status chip и количество ограничений | открыть ограничения; downstream-действие допускается только с сохранением ограничений |
| `NOT_READY` | `В работе` | Для текущего scope ещё нужны внутренние действия, проверка или применение одобренного изменения | синий/нейтральный status chip | открыть текущее состояние; пользовательское действие показывается только при наличии адресного вопроса |
| `BLOCKED` | `Заблокирован` | Продолжение невозможно до конкретного внешнего события или решения; получен валидный active `block_id` | красный status chip, `block_id`, ответственная сторона и условие возобновления | выполнить адресное действие, если пользователь назначен ответственным; иначе только просмотр |

Интерфейс хранит и передаёт machine-readable status без перевода. Русское название является только пользовательской подписью.

#### 9.6.2. Состояния наличия Паспорта

`Паспорт отсутствует` не является пятым состоянием Паспорта. Это отдельный результат поиска, означающий, что для подтверждённого точного SKU канонический Паспорт не найден.

| Состояние | Отображение | Доступное действие |
|---|---|---|
| Точный SKU подтверждён, Паспорт не найден | серый индикатор `Паспорт отсутствует` | `Создать Паспорт` |
| SKU не подтверждён | предупреждение `Требуется точный SKU` | выбрать или ввести точный SKU; создание недоступно |
| Найдено несколько возможных записей | предупреждение `Возможный дубликат` | `Сравнить` |

#### 9.6.3. Необходимость действия пользователя

Индикатор `Требуется моё действие` рассчитывается отдельно от состояния Паспорта.

Он имеет значение `Да` только когда существует активный объект, для которого текущий пользователь или его роль указаны ответственными:

- вопрос Верификатора со статусом `SENT`;
- активный `BLOCKED` с внешним условием, назначенным пользователю;
- конфликт значений, по которому требуется одно из разрешённых решений;
- иной адресный запрос, отдельно определённый утверждённым сценарием вкладки.

`NOT_READY` само по себе не означает, что требуется действие пользователя. Если работа выполняется внутри конвейера, строка показывает `Действие не требуется` и не предлагает ручной запуск агента.

Отправленный вопрос `SENT` сам по себе не переводит Паспорт в `BLOCKED`. При отсутствии валидного active block record интерфейс сохраняет состояние `NOT_READY / В работе` и отдельно показывает `Требуется ответ`. `BLOCKED / Заблокирован` разрешён только при наличии `BLK-<RUN>-<NNN>`, причины, ответственной стороны и условия возобновления.

#### 9.6.4. Актуальность данных Реестра

Технические состояния не заменяют состояние Паспорта и отображаются отдельным предупреждением:

| Техническое состояние | Значение | Поведение интерфейса |
|---|---|---|
| `Актуально` | версия и SHA подтверждены | доступны действия согласно состоянию Паспорта |
| `Обновляется` | Реестр ожидает принятый результат текущего запуска | разрешён просмотр; дублирующий запуск недоступен |
| `Данные устарели` | версия или SHA не совпадают с актуальным источником | изменяющие действия недоступны; интерфейс показывает предупреждение и автоматически повторяет read-only refresh/reconciliation по системной политике |
| `Ошибка загрузки` | состояние Паспорта нельзя достоверно получить | показывается последнее подтверждённое состояние с датой и предупреждением; запуск недоступен |

#### 9.6.5. Приоритет отображения

1. Сначала показывается проблема identity: точный SKU не определён или найден возможный дубликат.
2. Затем — техническое предупреждение об актуальности данных.
3. Затем — каноническое состояние Паспорта.
4. Отдельно — индикатор необходимости действия пользователя.
5. Следующее действие определяется только после применения всех четырёх уровней.

Цвет не является единственным носителем смысла: каждый индикатор содержит текст, а для блокера — ответственную сторону и условие возобновления.

Пользовательская кнопка `Синхронизировать` не используется: для неё нет агентского route. Техническое обновление данных Реестра является системной read-only операцией и не запускает агента, новый run или изменение Паспорта.

### 9.7. Правила следующего действия

| Условие | Основное действие | Переход |
|---|---|---|
| Паспорт отсутствует, SKU подтверждён | `Создать Паспорт` | `Создание Паспорта` |
| `READY`, действий пользователя нет | `Открыть Паспорт` | read-only просмотр |
| `READY_WITH_LIMITATIONS` | `Открыть ограничения` | объект ограничения/история решения |
| Есть вопрос со статусом `SENT` | `Ответить` | `Взаимодействие с Верификатором` |
| Есть `BLOCKED` и пользователь является ответственным | `Выполнить требуемое действие` | адресный объект блокера |
| `NOT_READY`, пользовательское действие не требуется | `Открыть работу` | текущий статус без ручного запуска агента |
| Найдены возможные дубликаты товара | `Сравнить` | выбор точного SKU |

Если одновременно применимы несколько условий, приоритет: конфликт identity → активный внешний блокер → отправленный вопрос → ограничение → просмотр. Интерфейс не объединяет разные действия в универсальную кнопку.

### 9.8. Пустые и ошибочные состояния

- Ничего не найдено: показать критерии поиска и действие `Создать Паспорт` только после подтверждения точного SKU.
- Несколько возможных SKU: потребовать выбор; запуск недоступен.
- Точный SKU неизвестен: запросить только SKU, не угадывать по модели или имени файла.
- Паспорт найден, но версия/SHA не подтверждены: просмотр возможен с предупреждением; изменяющие действия заблокированы.
- Агентский маршрут недоступен: показать причину и `BLOCKED`, не предлагать ручной обход.
- Папка недоступна: показать отказ внешней системы доступа; не менять права автоматически.

### 9.9. Запрещённые действия

- редактирование Product Truth из таблицы или карточки;
- ручной выбор агента и этапа конвейера;
- создание второго Паспорта для существующего точного SKU;
- кнопка `Передать новые данные`;
- автоматический повторный аудит или верификация из факта просмотра;
- представление генерации креатива как обновления Паспорта.
- запуск `Передать новые данные` без нового source artifact и точного SKU.

### 9.10. Acceptance tests

1. По точному SKU находится одна актуальная запись Паспорта либо состояние `Паспорт отсутствует`.
2. По названию с несколькими совпадениями запуск недоступен до выбора SKU.
3. Для `READY_WITH_LIMITATIONS` пользователь видит ограничения до перехода к downstream-действиям.
4. Для отправленного вопроса основная кнопка ведёт к конкретному question ID.
5. Для `BLOCKED` показаны ответственная сторона и условие возобновления.
6. `Открыть Паспорт` не предоставляет редактирование.
7. `Открыть папку материалов` не расширяет права пользователя.
8. В строке, карточке и меню отсутствует действие `Передать новые данные`.
9. При неизвестной версии/SHA нельзя запустить изменяющее действие.
10. Переход сохраняет точный SKU и версию товара.
11. `NOT_READY` без адресного запроса показывает `Действие не требуется`, а не кнопку ответа или запуска агента.
12. `Паспорт отсутствует` не передаётся как состояние Паспорта.
13. Техническое состояние `Данные устарели` не изменяет последний подтверждённый статус Паспорта, но блокирует изменяющие действия.
14. Любой цветной статус имеет текстовую подпись; блокер показывает ответственную сторону и условие возобновления.
15. Question `SENT` без active `block_id` не отображается как `BLOCKED`.
16. При `Данные устарели` отсутствует пользовательская кнопка `Синхронизировать`; изменяющие действия заблокированы до системного refresh/reconciliation.

## 10. Вкладка «Создание Паспорта»

Статус раздела: `APPROVED`  
Готовность контракту замены: `READY_FOR_IMPLEMENTATION`; feature flag `OFF`  
Готовность binding додавання даних: `READY_FOR_IMPLEMENTATION`; feature flag `OFF`  
Статус визуализации: `APPROVED`

### 10.1. Назначение

Вкладка используется для передачи исходных материалов по точному SKU. Если Паспорт отсутствует, пользователь запускает его первичное создание. Если Паспорт существует, пользователь может передать новые данные в ограниченный delta-сценарий либо отдельно запустить полную замену Паспорта через два подтверждения.

После запуска эта же вкладка показывает контрольный результат. Если Верификатору требуется ответ пользователя, вкладка показывает уведомление с question ID, кратким описанием влияния на Паспорт и действием `Перейти к вопросу`. Ответ вводится только во вкладке `Взаимодействие с Верификатором`.

Вкладка не позволяет напрямую редактировать существующий Паспорт и не показывает внутренние переходы между агентами как пользовательские этапы.

### 10.2. Точки входа

Вкладка открывается:

- из `Реестра Паспортов` по действию `Создать Паспорт` для подтверждённого точного SKU;
- напрямую из навигации `Контент → Паспорт SKU → Создание Паспорта`;
- по возврату к незавершённому созданию того же SKU;
- из `Реестра Паспортов` по действию `Передать новые данные` для существующего Паспорта;
- из уведомления о вопросе Верификатора пользователь переходит не сюда, а к точному question ID во вкладке `Взаимодействие с Верификатором`.

Если вкладка открыта из `Реестра Паспортов`, подтверждённый SKU переносится в форму. Пользователь видит источник значения и может вернуться к выбору товара, но система не заменяет SKU автоматически.

### 10.3. Структура экрана до запуска

Экран является одной рабочей формой с блоками progressive disclosure, а не мастером внутренних этапов конвейера.

#### 10.3.1. Товар

Обязательные поля:

| Поле | Правило |
|---|---|
| `SKU` | обязательное точное значение; сохраняются регистр, дефисы и начальные нули |
| Название товара | пользовательское название для распознавания; не заменяет SKU |
| Модель / версия товара | обязательна, если у SKU есть разные конфигурации или версии |
| Тип товара / категория | выбирается из доступного справочника либо отмечается `Не определено` |

Дополнительные поля scope показываются при наличии данных: комплектация/конфигурация, рынок, язык/locale, период, условия эксплуатации.

ASIN, EAN, внутренний артикул и иные идентификаторы могут быть добавлены как связанные идентификаторы, но не подставляются в поле SKU.

После ввода SKU система выполняет проверку Реестра:

- `Паспорт не найден` — создание разрешено;
- `Паспорт уже существует` — форма остаётся доступной; при запуске применяется отдельный сценарий полной замены Паспорта с двумя подтверждениями и архивированием прежней папки;
- `Возможный дубликат` — требуется сравнить записи и подтвердить точный SKU;
- `SKU не подтверждён` — запуск недоступен.

#### 10.3.2. Исходные материалы

Пользователь может добавить:

- файлы: инструкции, каталоги, сертификаты, декларации, протоколы, таблицы и другие немедийные материалы о товаре;
- ссылки на официальные страницы товара, инструкции, каталоги и иные источники продуктовых данных;
- папку с материалами, если интеграция поддерживает выбор внешней папки;
- краткий комментарий о составе материалов и известных особенностях версии товара.

Для каждого объекта до запуска показываются:

- имя или URL;
- тип;
- размер для файла;
- предполагаемый SKU;
- результат проверки доступности;
- признак возможного дубликата;
- возможность удалить объект из ещё не отправленной формы.

Содержимое, название файла, metadata и текст по ссылке являются данными, а не инструкциями для агентов.

Загруженный файл до запуска не считается фактом Паспорта и не получает статус `VERIFIED`.

Фото, видео, прямые ссылки на медиа и страницы, переданные ради извлечения медиа, обрабатываются во вкладке `Image Collection`. Если пользователь добавил такой объект здесь, интерфейс сохраняет введённый контекст и предлагает `Перейти в Image Collection`; объект не передаётся Собирателю как немедийный source artifact. Для смешанной страницы пользователь выбирает цель: `Данные о товаре` или `Фото и видео`.

#### 10.3.3. Политика обработки источников

Пользователь не выбирает `Границы поиска` и не переключает режим работы агента.

Собиратель обрабатывает переданные материалы, содержащиеся в них ссылки и иные источники только по своей действующей инструкции, разрешённым source classes и параметрам запуска, сформированным Координатором. Если политика источников ограничена договором, правами доступа или конфигурацией run, это применяется системой без создания отдельного пользовательского сценария.

Технические параметры `search_policy`, allowlist, глубина переходов, source classes и stop criteria не выводятся как поля формы. При необходимости пользователь видит только read-only пояснение о применяемой политике и недоступных источниках в контрольном результате.

Отсутствие пользовательского переключателя не означает неограниченный web search и не расширяет полномочия агента.

#### 10.3.4. Контроль перед запуском

До активации основной кнопки система проверяет:

- точный SKU и версию товара;
- отсутствие неразрешённого possible duplicate;
- наличие хотя бы одного исходного материала, который успешно прошёл проверку доступности;
- доступность добавленных файлов и ссылок либо явное исключение недоступного объекта пользователем;
- возможность создать `product_root` внутри проекта результатов;
- доступность Координатора и обязательных контрактов;
- подтверждение выбранного действия: первичное создание, передача новых данных либо полная замена.

Технические поля `run_id`, `product_root`, idempotency key, версии/SHA контрактов и `verifier_mode=MVP` формирует и проверяет система. Пользователь их не заполняет.

Кнопки `Создать Паспорт`, `Создать новый Паспорт` и `Передать новые данные` неактивны, пока блок `Исходные материалы` пуст либо все добавленные объекты имеют ошибку доступности. Заполнение только описания материалов не активирует действие. Для запуска также должны быть выполнены остальные обязательные проверки identity и preflight.

### 10.4. Основное действие

Основное действие зависит от наличия Паспорта:

- если Паспорт отсутствует — `Создать Паспорт`;
- если Паспорт существует — основной безопасный action `Передать новые данные`, а destructive action `Создать новый Паспорт` показывается отдельно.

Обе кнопки активируются только после добавления хотя бы одного доступного исходного материала и выполнения обязательных identity/preflight-проверок.

### 10.4.1. Передача новых данных в существующий Паспорт

Если Паспорт существует, рядом с блоком исходных материалов показывается панель `Что сделать с материалами?`.

Основная кнопка: `Передать новые данные`.

Пояснение:

> Новые материалы будут сравнены с текущим Паспортом. Паспорт изменится только после проверки данных. Дубликаты не создадут новую версию, а конфликтующие значения потребуют отдельного решения.

Перед отправкой пользователь видит:

- точный SKU;
- текущую версию Паспорта;
- перечень новых материалов;
- scope сравнения `Все переданные материалы`;
- предупреждение, что передача не подтверждает содержащиеся в материалах факты.

Нажатие `Передать новые данные` формирует `requested_action=SUBMIT_SOURCE_EVIDENCE_DELTA` по `Listing_Suite_Integration_Contract.md`. После validation Координатор связывает action с run mode `source_evidence_delta`. Пользователь не выбирает агента и не управляет внутренними переходами.

Разрешённый маршрут:

`Координатор → Собиратель compare/reconcile → [целевой Аудитор → Верификатор только при конфликте или evidence-decision] → Собиратель apply → STOP`.

Результаты обработки:

| Результат | Значение для пользователя | Изменение Паспорта | Следующее действие |
|---|---|---|---|
| `DUPLICATE_EXACT` | этот же файл уже зарегистрирован | нет | открыть результат |
| `DUPLICATE_SEMANTIC` | материал не содержит новых данных относительно уже обработанного источника | нет | открыть сравнение |
| `NEW_SUPPORTING_EVIDENCE` | новый материал подтверждает существующее значение | после регистрации evidence link создаётся новая версия того же Паспорта без автоматического повышения verification status | открыть обновлённый Паспорт |
| `NEW_ADDITIVE_FACT` | найден новый непротиворечивый факт | в тот же Паспорт добавляется `PROPOSED/UNVERIFIED` fact с provenance и создаётся новая версия | открыть обновлённый Паспорт |
| `CONFLICTING_VALUE` | новое значение противоречит текущему | автоматической замены нет | ответить на адресный вопрос |
| `WRONG_SKU_OR_SCOPE` | материал не относится к выбранному SKU или scope | материал архивируется, но не применяется к target SKU | выбрать правильный SKU либо исключить материал |
| `STANDARDS_OR_CREATOR_INSTRUCTION` | материал содержит стандарт, шаблон или инструкцию для Creator, а не факты товара | Паспорт не изменяется | открыть результат классификации |

Недоступность файла/URL и нарушение технического входного контракта отображаются отдельно как access/preflight error и не создают новый `delta_disposition`.

Для `CONFLICTING_VALUE` Верификатор показывает текущее и новое значение, оба источника и разрешённые решения `KEEP_CURRENT`, `ACCEPT_NEW`, `KEEP_DISPUTED`, `NOT_APPLICABLE`. Только одобренное изменение применяется Собирателем к тому же физическому Паспорту.

После запуска интерфейс использует состояния:

- `Данные переданы` — Координатор принял вход;
- `Сравнение материалов` — выполняется compare/reconcile, действие пользователя не требуется;
- `Требуется решение` — обнаружен конфликт или недостаточно evidence;
- `Паспорт дополнен` — `NEW_SUPPORTING_EVIDENCE` или `NEW_ADDITIVE_FACT` применены к тому же Паспорту и подтверждены receipt;
- `Без изменений` — материал признан дубликатом или не дал новых данных;
- `Ошибка обработки` — показана адресная причина и допустимое повторное действие.

Повторная отправка того же набора с тем же idempotency key не создаёт новый run и не увеличивает версию Паспорта.

#### Контрактная готовность сценария добавления

00A описывает `source_evidence_delta`, а `Listing_Suite_Integration_Contract.md` v1.1 связывает кнопку с exact request schema, Coordinator action `SUBMIT_SOURCE_EVIDENCE_DELTA`, idempotency rule и пользовательским receipt. Contract tests пройдены; до implementation/integration-test PASS feature flag остаётся `OFF`, поэтому сценарий ещё не production-active.

### 10.4.2. Создание при отсутствии Паспорта

Если для подтверждённого SKU канонический Паспорт отсутствует, после успешного preflight нажатие `Создать Паспорт` запускает обычный initial run без дополнительного предупреждения о замене.

Нажатие означает разрешение:

- зарегистрировать переданные материалы как вход текущего SKU;
- создать один initial run через Координатора;
- выполнить разрешённый автоматический маршрут первичного создания;
- сформировать первый контрольный результат либо адресный запрос пользователю.

Нажатие не означает:

- подтверждение фактов из материалов;
- разрешение на публикацию или генерацию контента;
- согласие с будущими спорными значениями;
- разрешение на создание второго Паспорта;
- разрешение на повторные полные прогоны.

После нажатия форма входа фиксируется. Изменение состава входа требует отмены до фактического старта либо отдельного разрешённого сценария после завершения; скрытая дозагрузка в работающий run запрещена.

### 10.4.3. Полная замена существующего Паспорта

Если для точного SKU уже существует Паспорт, кнопка `Создать Паспорт` остаётся доступной после заполнения исходных материалов, но её нажатие не запускает работу немедленно.

Система последовательно показывает два подтверждения.

**Первое подтверждение**

Заголовок: `Создать новый Паспорт вместо существующего?`

Описание:

> При создании нового Паспорта существующий Паспорт и его рабочая папка будут перемещены в архив и скрыты из текущей работы. Вы уверены, что хотите создать новый Паспорт? Если вы хотите дополнить материалы существующего Паспорта, воспользуйтесь функцией «Передать новые данные».

Действия:

- `Отменить` — закрывает сообщение и сохраняет заполненную форму;
- `Продолжить создание нового Паспорта` — открывает второе подтверждение.

**Второе подтверждение**

Заголовок: `Подтвердите создание нового Паспорта для SKU <SKU>`

Описание:

> Вы подтверждаете создание нового Паспорта для SKU <SKU>. Текущий Паспорт версии <passport_version> и его материалы будут перемещены в архив. Это действие нельзя отменить из кабинета.

Для защиты от ошибки во втором сообщении повторно показываются SKU, название/модель товара и текущая версия Паспорта.

Действия:

- `Вернуться` — возвращает к первому подтверждению без запуска;
- `Да, создать новый Паспорт` — разрешает архивирование и новый запуск.

До второго подтверждения текущий Паспорт, его папка и материалы не изменяются.

После второго подтверждения система выполняет атомарный переход:

1. Проверяет, что версия и SHA текущего Паспорта не изменились после показа подтверждения.
2. Создаёт immutable archive receipt со SKU, версией Паспорта, SHA, исходным и архивным путём, временем и пользователем, подтвердившим замену.
3. Перемещает прежнюю папку Паспорта в архив и скрывает её из текущего интерфейса.
4. Не удаляет архив физически в рамках пользовательской операции.
5. Создаёт новую рабочую папку того же SKU и запускает создание нового канонического Паспорта по зафиксированным исходным материалам.
6. Связывает новый Паспорт с архивным через `replaces_passport_id` и archive receipt.

Если проверка версии/SHA, архивирование или создание новой папки не завершились, новый run не запускается, а старый Паспорт остаётся каноническим и видимым. Частичное состояние, в котором прежний Паспорт скрыт, но новый не создан, запрещено.

Физическое удаление архивной папки выполняется только администратором после отдельного retention period и не входит в действие пользователя `Создать Паспорт`. Срок хранения, полномочия администратора, журнал удаления и возможность восстановления должны быть определены отдельной политикой.

#### Контрактная готовность сценария

Сценарий имеет статус `READY_FOR_IMPLEMENTATION`: 00A v2.13 определяет отдельный route полной замены, archive receipt, atomic switch, lineage и `replaces_passport_id`. До implementation/integration-test PASS feature flag остаётся `OFF`.

Интерфейс и два подтверждения разрешены к реализации и тестированию. Пока feature flag выключен, второе подтверждение возвращает `FEATURE_DISABLED` и не выполняет production-операцию.

Ссылка `Передать новые данные` в первом предупреждении закрывает сообщение, сохраняет заполненные материалы и переводит фокус к безопасному действию передачи данных. При выключенном feature flag отправка typed request не выполняется.

### 10.5. Состояния создания

| Состояние интерфейса | Значение | Что видит пользователь | Доступное действие |
|---|---|---|---|
| `Черновик` | форма ещё не отправлена | редактируемые поля и материалы | `Создать Паспорт` после preflight |
| `Проверка входа` | система проверяет identity, материалы и контракты | результаты проверок по объектам | исправить только найденные ошибки |
| `Создание запущено` | Координатор принял запуск | SKU, время запуска, состав зафиксированного входа и сообщение `Действий не требуется` | открыть контрольный статус или выйти из вкладки |
| `Требуется ответ` | Верификатор сформировал адресный вопрос | уведомление с question ID, кратким вопросом и влиянием на Паспорт | `Перейти к вопросу` |
| `Заблокировано` | требуется конкретное внешнее условие | причина, ответственная сторона и условие возобновления | выполнить адресное действие, если оно назначено пользователю |
| `Паспорт создан` | первичный маршрут завершён с допустимым состоянием Паспорта | состояние, версия, ограничения и контрольный результат | `Открыть Паспорт` |
| `Ошибка запуска` | Координатор не принял запуск или обязательный контракт недоступен | точная причина без ложного создания run | исправить вход или повторить preflight |
| `Подтверждение замены` | для SKU уже существует Паспорт | две последовательные карточки подтверждения с SKU и текущей версией | отменить либо дважды подтвердить замену |
| `Архивирование` | после второго подтверждения выполняется защищённое переключение | неизменяемый статус операции без повторного нажатия | дождаться результата; при ошибке старый Паспорт остаётся текущим |
| `Сравнение материалов` | новые материалы переданы в `source_evidence_delta` | текущая версия Паспорта остаётся доступной | дождаться результата без повторного запуска |
| `Требуется решение` | найден конфликт нового и текущего значения | обе версии видимы, автоматической замены нет | ответить на адресный вопрос |
| `Паспорт дополнен` | approved data/evidence применены к тому же Паспорту | версия Паспорта увеличена, receipt подтверждён | открыть обновлённый Паспорт |
| `Без изменений` | получен duplicate/no-new-data result | версия Паспорта не меняется | открыть результат сравнения |

Это состояния пользовательской задачи создания, а не новые Run statuses и не состояния Паспорта.

### 10.6. Переход к взаимодействию с Верификатором

Если Верификатору необходимы сведения, вкладка показывает уведомление, не превращаясь в форму ответа. Уведомление содержит stable question ID, один конкретный вопрос, причину запроса, влияние на готовность Паспорта и действие `Перейти к вопросу`.

Переход открывает точный question ID во вкладке `Взаимодействие с Верификатором` с сохранёнными SKU, версией товара и контекстом запуска. Поля ответа, вложения, решения по конфликту и история диалога существуют только там. Если открытых вопросов несколько, здесь показываются их количество и ссылка на очередь выбранного SKU.

### 10.7. Контрольный результат

После завершения пользователь видит:

- точный SKU и версию товара;
- ссылку на единый Паспорт;
- `passport_version`;
- состояние `NOT_READY`, `BLOCKED`, `READY_WITH_LIMITATIONS` или `READY` с пользовательской подписью;
- ограничения и блокеры;
- количество открытых вопросов;
- дату и время последнего принятого результата;
- ссылку на папку материалов;
- одно следующее действие.

Технические handoff, manifest и receipts доступны в раскрываемом блоке `Детали запуска`, но не конкурируют с пользовательским результатом.

### 10.8. Ошибки и особые случаи

- Если точный SKU не найден в материалах, система задаёт один вопрос о SKU до создания `run_id` и `product_root`.
- Если разные материалы содержат конфликтующие SKU, запуск блокируется до выбора точного товара.
- Если Паспорт появился между preflight и отправкой, обычный запуск останавливается и пользователю показывается сценарий полной замены; без двух подтверждений новый Паспорт не создаётся.
- Если версия или SHA существующего Паспорта изменились между подтверждением и архивированием, операция прекращается и требует повторного просмотра актуальной версии.
- Недоступный файл или URL показывается пообъектно. Пользователь может заменить его либо явно исключить из scope до запуска.
- Отсутствие категорийного профиля не скрывается: оно передаётся как gap, но не заменяется выдуманной структурой.
- Закрытие страницы после принятого запуска не отменяет работу; при возврате открывается текущая задача создания.
- Повторное нажатие с тем же idempotency key не создаёт второй run.

### 10.9. Запрещённые действия

- ручной выбор Собирателя, Аудитора или Верификатора;
- показ внутренних handoff как шагов, которые должен подтвердить пользователь;
- создание нового Паспорта при наличии канонического Паспорта без двух подтверждений и принятого контракта замены;
- немедленное физическое удаление прежней папки пользовательским действием;
- скрытие старого Паспорта до успешного archive receipt и готовности создать новую папку;
- редактирование Product Truth из формы создания;
- добавление материалов в уже работающий run без отдельного разрешённого сценария;
- передача свободного текста как изменения Product Truth без source artifact;
- полный повторный сбор под названием `Передать новые данные`;
- автоматический запуск Content TZ, AI Creator или публикации после создания Паспорта.

### 10.10. Acceptance tests

1. Без точного SKU основная кнопка недоступна, а система задаёт один адресный вопрос.
2. Модель, ASIN, EAN или имя файла не подставляются как SKU.
3. Кнопка `Создать Паспорт` активируется только при наличии хотя бы одного доступного исходного материала и выполненных обязательных identity/preflight-проверках.
4. Possible duplicate блокирует запуск до явного выбора точного SKU.
5. Пользователь может передать несколько файлов и ссылок и видит результат проверки каждого объекта.
6. Пользователь не выбирает search policy; применённая техническая политика фиксируется системой в деталях запуска.
7. После запуска пользователь не подтверждает внутренние передачи между агентами.
8. При отсутствии запроса интерфейс показывает `Действий не требуется`.
9. Уведомление о вопросе содержит stable question ID и действие `Перейти к вопросу`, но не содержит полей ответа.
10. Переход открывает точный вопрос во вкладке `Взаимодействие с Верификатором` с сохранённым контекстом SKU и запуска.
11. Решения по конфликту и вложения доступны только во вкладке `Взаимодействие с Верификатором`.
12. Повторная отправка того же запуска не создаёт второй run или второй Паспорт.
13. Результат показывает состояние и версию единого Паспорта, ограничения, блокеры и следующее действие.
14. Создание Паспорта не запускает генерацию контента или публикацию.
15. Для существующего Паспорта показаны два последовательных подтверждения; отмена на любом из них не изменяет текущий Паспорт.
16. Второе подтверждение повторно показывает точный SKU, название/модель и текущую версию Паспорта.
17. При изменении версии/SHA после подтверждения замена не выполняется.
18. Архивирование создаёт receipt и сохраняет связь старого и нового Паспортов.
19. Ошибка архивирования не скрывает старый Паспорт и не запускает создание нового.
20. Пользовательская операция не удаляет архив физически.
21. До ввімкнення feature flag другий confirm не викликає production-операцію і повертає `FEATURE_DISABLED`; після ввімкнення він лише завершує typed request, а не самостійно архівує або створює Паспорт.
22. Для существующего Паспорта безопасным основным action является `Передать новые данные`, а `Создать новый Паспорт` визуально отделён как destructive action.
23. `Передать новые данные` невозможно без хотя бы одного нового доступного source artifact.
24. Exact и semantic duplicate не увеличивают версию Паспорта.
25. `NEW_SUPPORTING_EVIDENCE` и `NEW_ADDITIVE_FACT` увеличивают версию только после регистрации/применения и receipt; они не становятся `VERIFIED` автоматически.
26. `CONFLICTING_VALUE` не перезаписывает текущее значение и создаёт адресный вопрос с четырьмя разрешёнными решениями.
27. Повторная отправка того же набора не создаёт второй delta-run.

### 10.11. Решения по реализации

- нужен ли комментарий пользователя как отдельное поле или только описание материалов;
- допускается ли выбор внешней папки в первой версии либо только файлы и ссылки;
- показывать ли дополнительные scope-поля сразу или раскрывать по действию `Уточнить товар`;
- лимиты количества и размера файлов задаются конфигурацией реализации; видео в этой вкладке не принимается;
- может ли пользователь отменить запуск после принятия Координатором, и если да — до какого состояния;
- при нескольких вопросах показываются счётчик и переход к очереди выбранного SKU; форма ответа внутри Создания Паспорта не дублируется;
- retention period архивной папки и полномочия администратора на физическое удаление;
- возможность восстановления архивного Паспорта;
- полная замена использует утверждённый `RECREATE_PASSPORT`, archive receipt и атомарное переключение;
- добавление данных использует утверждённый `SUBMIT_SOURCE_EVIDENCE_DELTA`;
- пользовательский result receipt различает duplicate, additive и conflict outcomes.

## 11. Вкладка «Взаимодействие с Верификатором»

Статус раздела: `APPROVED`  
Статус визуализации: `APPROVED`

### 11.1. Назначение

Вкладка является единой очередью вопросов **Агента-Верификатора к человеку, ответственному за данные конкретного SKU**. Пользователь видит, что именно Верификатор просит уточнить или подтвердить, отвечает в контексте конкретного вопроса, прикладывает подтверждающий материал и отслеживает результат проверки ответа.

Вопрос создаёт Верификатор, когда после принятого сбора и аудита либо обработки новых данных остаётся один из случаев:

- отсутствует обязательная информация, которую невозможно получить из доступных источников;
- требуется конкретный документ или ссылка;
- источники содержат конфликтующие значения;
- необходимо решение уполномоченного владельца данных;
- полученный ранее ответ оказался частичным или недостаточным.

Адресатом вопроса является не любой пользователь кабинета, а назначенный ответственный: владелец SKU, владелец конкретного типа данных, уполномоченный эксперт либо другой respondent, указанный в question record.

Собиратель и Аудитор не ведут здесь самостоятельные диалоги с пользователем. Они передают обнаруженный gap/conflict по контракту, после чего Верификатор формирует один адресный вопрос человеку. Внутренние технические вопросы между агентами пользователю не показываются.

Вкладка не является свободным чатом с агентом и не предназначена для вопросов пользователя Верификатору. Каждый диалог начинается только из зарегистрированного Верификатором question ID формата `Q-<RUN>-<NNN>` и связан с точным SKU, версией Паспорта, gap/conflict и ожидаемым результатом.

Форма ответа, решения по конфликту и полная история существуют только в этой вкладке. Из `Создания Паспорта` пользователь переходит сюда по exact question ID.

### 11.2. Точки входа

- основная навигация `Контент → Паспорт SKU → Взаимодействие с Верификатором`;
- действие `Ответить` из `Реестра Паспортов`;
- уведомление `Требуется ответ` внутри `Создания Паспорта`;
- уведомление о новом или повторно открытом вопросе;
- переход из конфликта или ограничения конкретного Паспорта.

При переходе из другого экрана автоматически выбираются точные `sku_id` и `question_id`. Пользователь может вернуться к общей очереди без потери контекста.

### 11.3. Структура экрана

Экран состоит из трёх зон:

1. фильтры и сводные счётчики;
2. очередь вопросов;
3. карточка выбранного вопроса и история диалога.

#### 11.3.1. Фильтры и счётчики

Показываются счётчики:

- `Требуют моего ответа`;
- `Ожидают проверки`;
- `Нужны уточнения`;
- `Решены`.

Доступны фильтры:

- SKU, название или модель;
- пользовательское состояние вопроса;
- влияние `Блокирует Паспорт / Требуется для готовности / Не блокирует`;
- тип запроса `Ответ / Документ / Решение конфликта`;
- дата создания или последнего изменения;
- ответственный пользователь/роль — если пользователь имеет право видеть чужие вопросы.

По умолчанию показываются вопросы `Требуют моего ответа` и `Нужны уточнения`.

#### 11.3.2. Очередь вопросов

Обязательные колонки:

| Колонка | Содержание |
|---|---|
| Товар / SKU | название, точный SKU и версия товара |
| Вопрос | краткий текст и stable question ID |
| Тип | ответ, документ или решение конфликта |
| Состояние | пользовательская подпись и machine-readable status в деталях |
| Влияние | блокирует Паспорт либо не блокирует |
| Создан / обновлён | дата последнего значимого события |
| Ответственный | пользователь или роль |
| Следующее действие | одно контекстное действие |

В строке не показывается полный внутренний gap package, технические manifests или рассуждение агента.

`Тип` и `Состояние` являются разными осями. Например, `Решение конфликта` — тип запроса, а его состоянием может быть `Требуется ответ`, `Ожидает проверки` или `Решён`. Тип не отображается вместо состояния.

Подпись `Блокирует Паспорт` разрешена только при наличии валидного active `BLK-<RUN>-<NNN>` с причиной, responsible party и resume condition. Question `SENT` без block record получает влияние `Требуется для готовности` либо `Не блокирует`, но не меняет состояние Паспорта на `BLOCKED`.

#### 11.3.3. Карточка выбранного вопроса

Карточка содержит:

- точный SKU, название и версию товара;
- состояние и версию Паспорта;
- stable question ID формата `Q-<RUN>-<NNN>`;
- полный текст одного вопроса;
- пояснение `Зачем это нужно`;
- затронутый факт, gap или conflict;
- ожидаемый тип ответа;
- критерий, при котором вопрос может быть решён;
- срок ответа, если он установлен;
- ответственную сторону;
- связанные источники, доступные пользователю;
- историю вопроса, ответов и решений.

Технические object IDs и evidence locators доступны в раскрываемом блоке `Детали`, но не являются основным содержанием карточки.

### 11.4. Типы вопросов

#### 11.4.1. Ответ пользователя

Поля:

- `Ответ` — текстовое поле с placeholder `Введите ответ на запрос Верификатора`;
- `Документ или ссылка` — необязательное, если вопрос допускает ответ без внешнего подтверждения;
- `Отправить ответ`.

Интерфейс показывает, достаточно ли текста либо обязательно приложить evidence. Ответ пользователя не становится Product Truth автоматически.

#### 11.4.2. Запрос документа или ссылки

Поля:

- загрузка файла;
- добавление ссылки;
- краткий комментарий к материалу;
- `Передать документ`.

До отправки выполняется проверка доступности. Оригинал регистрируется как immutable Source Artifact; PDF или скан не отклоняется только из-за формата, но может требовать извлечения данных.

#### 11.4.3. Решение конфликта

Карточка показывает две стороны:

- текущее значение и его источник;
- новое значение и его источник;
- scope и условия каждого значения;
- последствия выбора.

Доступны только четыре решения с пользовательскими подписями:

| Machine-readable decision | Подпись в интерфейсе |
|---|---|
| `KEEP_CURRENT` | `Оставить текущее значение` |
| `ACCEPT_NEW` | `Принять новое значение` |
| `KEEP_DISPUTED` | `Сохранить как спорное` |
| `NOT_APPLICABLE` | `Не относится к этому SKU / scope` |

Выбор регистрируется как Answer/Decision Event. Даже `ACCEPT_NEW` не означает автоматический `VERIFIED`: изменение остаётся candidate до проверки authority/evidence и применения Собирателем.

### 11.5. Пользовательские состояния вопросов

| Пользовательское состояние | Нормативное основание | Значение | Следующее действие |
|---|---|---|---|
| `Требуется ответ` | `SENT` | вопрос доставлен и ждёт пользователя | `Ответить` |
| `Черновик ответа` | локальный UI draft | ответ ещё не передан агенту | `Продолжить` или `Удалить черновик` |
| `Ответ получен` | `ANSWER_RECEIVED` | неизменяемая версия ответа зарегистрирована | ожидать проверки |
| `Ожидает проверки` | Answer `RECEIVED` | Верификатор ещё не принял решение | открыть отправленный ответ |
| `Нужно уточнение` | Answer `PARTIAL` либо новый follow-up question | данных недостаточно | `Уточнить ответ` |
| `Ответ отклонён` | Answer `REJECTED` | показана адресная причина отклонения | передать исправленный ответ/evidence |
| `Решён` | Question `RESOLVED` после принятого решения и необходимого apply receipt | действие завершено | открыть историю |
| `Отменён / неактуален` | superseded/out-of-scope decision | ответ больше не требуется | открыть основание |

`ANSWER_RECEIVED` не закрывает вопрос. `RESOLVED` показывается только после выполнения нормативного closure, включая применение одобренного изменения, если оно требовалось.

### 11.6. Отправка и версии ответа

Перед отправкой пользователь видит точный SKU, question ID и перечень вложений.

После нажатия `Отправить ответ`:

1. создаётся неизменяемая версия Answer Artifact;
2. фиксируются автор, время, текст, файлы/ссылки и source artifact IDs;
3. состояние меняется на `Ответ получен`;
4. редактирование отправленной версии запрещается;
5. при необходимости исправления создаётся новая версия ответа, связанная с предыдущей.

Повторное нажатие с тем же idempotency key не создаёт второй ответ.

Черновик может сохраняться автоматически в кабинете, но не передаётся Верификатору и не изменяет состояние вопроса.

### 11.7. Массовые и внешние ответы

Для развёрнутых ответов пользователь может скачать и вернуть DOCX-форму. Для массового табличного сбора доступен канонический XLSX-шаблон. PDF используется как view copy, но фактически возвращённый PDF или скан принимается как immutable source artifact.

Импортированная форма должна содержать stable question IDs. Строки без надёжного ID не сопоставляются по порядку и получают `IDENTIFICATION_ERROR`.

Доступные действия:

- `Скачать форму вопросов`;
- `Загрузить заполненную форму`;
- `Экспортировать выбранные вопросы в XLSX` — только для разрешённого массового режима.

### 11.8. История диалога

История отображает в хронологическом порядке:

- создание и отправку вопроса;
- каждую версию ответа;
- прикреплённые source artifacts;
- результат проверки `VERIFIED`, `PARTIAL` или `REJECTED`;
- follow-up question;
- decision event;
- применение изменения и change event;
- закрытие, supersede или вывод из scope.

История read-only. Пользователь не удаляет отправленные ответы и решения.

### 11.9. Ошибки и особые случаи

- Если версия/SHA Паспорта изменилась и вопрос устарел, отправка блокируется до reconciliation; вопрос не закрывается молча.
- Если вложение недоступно, остальные данные сохраняются в черновике, но отправка с обязательным evidence недоступна.
- Если вопрос относится не к выбранному SKU, пользователь сообщает `Не относится к этому SKU`; это создаёт решение, а не удаляет вопрос.
- Если пользователь не имеет полномочий принять owner decision, интерфейс позволяет передать evidence, но не показывает закрытые decision actions.
- Если несколько вопросов имеют один intent, интерфейс показывает возможный дубликат; объединение выполняется только по нормативному решению.
- Закрытый вопрос не открывается повторно без нового основания и нового события.

### 11.10. Запрещённые действия

- свободный чат без question ID;
- изменение текста вопроса пользователем;
- ручная установка `RESOLVED`;
- прямое применение candidate update;
- редактирование или удаление отправленного ответа;
- сопоставление импортированных ответов по порядку строк без stable ID;
- представление ответа владельца как автоматически подтверждённого Product Truth;
- повторный полный аудит из факта получения ответа.

### 11.11. Acceptance tests

1. Действие `Ответить` из `Реестра Паспортов` открывает точные SKU и question ID.
2. По умолчанию пользователь видит вопросы, требующие его ответа или уточнения.
3. Каждый вопрос показывает причину, ожидаемый тип ответа и критерий решения.
4. Отправить ответ без обязательного evidence невозможно.
5. После отправки создаётся неизменяемая версия ответа, которую нельзя редактировать.
6. `ANSWER_RECEIVED` отображается как ожидание проверки, а не как решённый вопрос.
7. `PARTIAL` создаёт адресное уточнение, сохраняя предыдущий ответ в истории.
8. `REJECTED` показывает конкретную причину и разрешённое следующее действие.
9. Конфликт показывает обе стороны и только четыре разрешённых решения.
10. `ACCEPT_NEW` не меняет Паспорт до проверки и apply receipt Собирателя.
11. `RESOLVED` появляется только после выполнения closure criteria.
12. DOCX/XLSX/PDF регистрируются как source artifacts с question IDs и версиями.
13. Ответ без надёжного question ID не сопоставляется по порядку.
14. Пользователь без decision authority не видит недоступные решения как активные кнопки.
15. Повторная отправка того же ответа не создаёт дубликат.
16. Внутренние handoff между агентами не требуют действий пользователя.

### 11.12. Решения по реализации

Следующие параметры уточняются при реализации и не изменяют утверждённый пользовательский сценарий:

- нужна ли отдельная вкладка `Все / Мои` или достаточно фильтра ответственного;
- сохранять ли локальный черновик автоматически и как долго;
- показывать ли срок ответа, если он не задан внешней системой;
- кто имеет право массово экспортировать вопросы и импортировать XLSX;
- нужны ли уведомления внутри кабинета, email или только счётчик во вкладке;
- максимальные размеры и типы вложений.

## 12. Вкладка «Image Collection»

Статус раздела: `APPROVED_FOR_IMPLEMENTATION`  
Готовность контрактов: `READY_FOR_IMPLEMENTATION`; feature flag `OFF`  
Статус визуализации: `APPROVED`

### 12.1. Назначение

Вкладка управляет on-demand контуром `Image Collector` для точного SKU. Пользователь видит уже собранные медиаисточники и assets, добавляет новые фото, видео или ссылки либо запускает поиск нового контента спустя время.

Алгоритм регистрирует источники, извлекает медиа, выполняет дедупликацию, квалификацию и review, после чего передаёт разрешённый `passport_media_delta` Собирателю Паспорта. Вкладка не запускает `AI Creator`, не создаёт контент и не предоставляет publication authority.

### 12.2. Условия открытия и точки входа

Вкладка открывается из основной навигации либо из действия выбранного SKU. До запуска требуется:

- точный `sku_id` и версия товара;
- один канонический Паспорт минимум в состоянии `NOT_READY`, успешно прошедший read-back;
- актуальные `passport_id`, версия и SHA;
- snapshot уже известных медиа и источников;
- отсутствие неразрешённого possible duplicate товара.

Если Паспорта ещё нет, интерфейс направляет пользователя в `Создание Паспорта`. После появления минимального канонического Паспорта пользователь возвращается в `Image Collection` с тем же SKU.

### 12.3. Существующие материалы

Сразу после выбора SKU экран показывает до запуска:

- количество зарегистрированных источников и assets;
- миниатюры принятых фото и видео;
- источники, дату сбора и доступность;
- признаки duplicate, review, quarantine и limitation;
- дату последнего collection и его purpose;
- открытые действия пользователя.

Отсутствие медиа отображается явно и не трактуется как ошибка Паспорта.

### 12.4. Назначение запуска

Каждый запуск имеет один purpose:

| Purpose | Пользовательский смысл |
|---|---|
| `INITIAL_COLLECTION` | первый сбор медиа после создания минимального Паспорта |
| `ADDITIONAL_DISCOVERY` | повторный поиск нового контента для существующей collection |
| `USER_MEDIA_INTAKE` | обработка файлов и ссылок, переданных пользователем |
| `RECOVERY_DELTA` | контролируемое восстановление или дополнение после ограниченного результата |

Кнопка `Обработать добавленные материалы` создаёт `USER_MEDIA_INTAKE`. Кнопка `Найти новые материалы` создаёт `INITIAL_COLLECTION` либо `ADDITIONAL_DISCOVERY` в зависимости от истории SKU. Пользователь не выбирает агента или внутренний маршрут.

### 12.5. Входные материалы

Поддерживаются типы:

- `IMAGE_FILE`;
- `VIDEO_FILE`;
- `DIRECT_IMAGE_URL`;
- `DIRECT_VIDEO_URL`;
- `MEDIA_PAGE_URL`;
- `MEDIA_FOLDER`, если интеграция выбора папки включена.

Для каждого объекта показываются тип, источник, доступность, предполагаемый SKU/revision, duplicate signal и возможность удалить объект из неотправленной формы. Выбор папки создаёт одноразовый snapshot и не расширяет права пользователя.

Документные источники без задачи извлечения медиа направляются в `Создание Паспорта`. Для смешанной страницы пользователь выбирает цель обработки. Автоматическая отправка объекта одновременно в оба контура запрещена.

### 12.6. Запуск и binding

Единый запуск использует `requested_action=START_MEDIA_COLLECTION` по [Binding and Result Contract v1.0](../04_Image_Collection/00_Product_Requirements/Image_Collection_Listing_Suite_Binding_and_Result_Contract_v1.0.md). Запрос содержит exact SKU/Product version, Passport и existing-media snapshots, purpose, sources, visual targets, search scope либо `LOCAL_ONLY`, product/collection roots, scope-bound confirmation и idempotency key.

Повтор идентичного запроса возвращает существующий collection/run. Изменение purpose, источников или scope создаёт новый запрос и требует нового подтверждения. Технические параметры поиска задаются контрактом и инструкцией агента, а не пользовательским переключателем `Границы поиска`.

### 12.7. Состояния

Интерфейс показывает ровно одно evidence-backed состояние:

| Состояние | Значение для пользователя |
|---|---|
| `NOT_STARTED` | запуск ещё не создан |
| `MATERIALS_REGISTERED` | вход принят и зарегистрирован |
| `SEARCH_RUNNING` | выполняется поиск/извлечение |
| `ACCESS_REQUIRED` | нужен lawful access artifact либо исключение source |
| `REVIEW_RUNNING` | выполняется квалификация и review |
| `USER_DECISION_REQUIRED` | требуется типизированное решение пользователя |
| `READY_FOR_CONFIRMATION` | collection готова к подтверждению |
| `COLLECTION_CONFIRMED` | пользователь подтвердил состав collection |
| `PASSPORT_TRANSFER_PENDING` | media delta передан, применение к Паспорту не подтверждено |
| `PASSPORT_TRANSFERRED` | получен `PASSPORT_DELTA_APPLIED` |
| `COMPLETED_WITH_LIMITATIONS` | работа завершена с явно показанными ограничениями |

Это UI projection, а не новый Run status и не состояние Паспорта.

### 12.8. Действия пользователя

Допустимы только типизированные действия:

- `CONFIRM_ASSET_SKU_REVISION`;
- `PROVIDE_LAWFUL_ACCESS_ARTIFACT`;
- `EXCLUDE_SOURCE_FROM_SCOPE`;
- `ACCEPT_PROPOSED_ASSET`;
- `REJECT_PROPOSED_ASSET`;
- `CONFIRM_COLLECTION_COMPLETE`.

Каждое действие содержит actor, exact collection/SKU, ожидаемые manifest version/SHA, target IDs и idempotency key. Stale input не применяется. Исключение source не удаляет provenance.

`COLLECTION_READY` устанавливается только после receipt `CONFIRM_COLLECTION_COMPLETE` из состояния `READY_FOR_HUMAN_REVIEW` и запрещён в `PILOT_REVIEW_ONLY`. До `PASSPORT_DELTA_APPLIED` интерфейс показывает `PASSPORT_TRANSFER_PENDING`, а не завершение обновления Паспорта.

### 12.9. Контрольный результат и история

Экран получает агрегированный UI result receipt и показывает:

- purpose и версию collection;
- количество существующих, новых, дублирующихся и недоступных sources;
- accepted, review, quarantine и rejected assets;
- открытые действия и ограничения;
- media gate и Passport delta status;
- одно следующее действие.

Base/new Passport version и SHA показываются только из `PASSPORT_DELTA_APPLIED`. История collection, решений и receipts доступна read-only внутри выбранного SKU; отдельная верхнеуровневая вкладка `История` не нужна.

### 12.10. Запрещённые действия

- запуск без точного SKU и минимального канонического Паспорта;
- смешивание assets разных SKU в одной collection;
- принятие proposed asset без разрешённого review/решения;
- скрытое расширение search scope;
- автоматическое изменение Product Truth без receipt Собирателя;
- запуск `AI Creator`, генерации контента или публикации;
- отображение `PASSPORT_TRANSFERRED` до `PASSPORT_DELTA_APPLIED`.

### 12.11. Acceptance tests

1. После выбора SKU до запуска показаны уже собранные источники и assets.
2. Первый запуск и последующий поиск нового контента различаются purpose, но используют один контур.
3. Пользователь может передать файлы, прямые media URL и страницы для извлечения медиа.
4. Фото/видео из `Создания Паспорта` маршрутизируются сюда без автоматического запуска.
5. Документный source без media intent маршрутизируется в `Создание Паспорта`.
6. Без минимального канонического Паспорта запуск недоступен.
7. Повтор идентичного запроса не создаёт второй collection/run.
8. `ACCESS_REQUIRED` показывает источник и разрешённые действия, не предлагает обход доступа.
9. Stale manifest/version блокирует типизированное действие.
10. `COLLECTION_CONFIRMED` не даёт права публикации.
11. До `PASSPORT_DELTA_APPLIED` отображается `PASSPORT_TRANSFER_PENDING`.
12. Результат показывает ограничения и одно следующее действие.

13. Ни одно действие области не запускает создание креативов или публикацию.

## 14. Блокеры

- отсутствует точный SKU или есть конфликт идентификаторов;
- не определён агентский сценарий для запрошенного действия;
- отсутствует обязательный контракт или Координатор недоступен;
- интерфейс не может подтвердить актуальную версию/SHA Паспорта;
- внешний ресурс недоступен текущему пользователю;
- для `Image Collection` не создан минимальный канонический Паспорт;
- feature flag требуемой mutation/integration остаётся `OFF`.

## 15. Межі доказовості

Документ определяет утверждённую продуктовую модель интерфейса и готовые к реализации bindings. Он не подтверждает production activation интеграции, авторизации, хранилища, запуска агентов или доставки receipts. Статус `APPROVED_FOR_IMPLEMENTATION` не равен `LIVE`: все feature flags остаются `OFF` до соответствующих integration-test receipts.

Утверждённые PNG фиксируют композицию экранов. Machine-readable статусы, идентификаторы, действия и переходы реализуются по этому ТЗ и указанным контрактам, если пример в PNG устарел.

## 16. Решения по реализации

С 04.10.2026 утверждено:

- `Передать новые данные` использует `SUBMIT_SOURCE_EVIDENCE_DELTA` и отдельный typed UI binding;
- `Выбрать папку` создаёт одноразовый рекурсивный local snapshot без subscription, symlink traversal или расширения прав;
- partial intake разрешён, если принят хотя бы один object;
- `Создать новый Паспорт` использует `RECREATE_PASSPORT`, два подтверждения одного authorized actor и atomic replace transaction;
- recreate создаёт новый `passport_id` в той же lineage, оставляя ровно один ACTIVE canonical Passport;
- old facts/verification не наследуются автоматически;
- downstream bindings старого SHA получают `STALE_PASSPORT_BINDING`;
- до commit действует automatic rollback, после commit — только отдельный administrative restore;
- mutation routes используют per-SKU lock и idempotency;
- physical deletion не является user operation;
- `Image Collection` использует `START_MEDIA_COLLECTION`, а завершение применения к Паспорту подтверждается только `PASSPORT_DELTA_APPLIED`;
- последующие агенты создания контента размещаются в области `Контент`, а не внутри `Паспорт SKU`.
