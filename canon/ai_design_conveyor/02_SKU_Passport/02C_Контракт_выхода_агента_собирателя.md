# Контракт выходного пакета агента-собирателя

Версия: 23  
Статус: pilot ready; production status requires acceptance tests  
Дата: 04.10.2026

## 1. Общий контракт

Цей пакет передається лише разом із поточною версією єдиного Паспорта за [00A — Контракт передач Паспорта SKU](00A_Контракт_передач_Паспорта_SKU.md) v2.13. П’ять перелічених нижче файлів — дозволені службові outputs, а не заміна Паспорта чи дозвіл створювати додаткові «проєкції». Manifest додатково фіксує `passport_id/version/state/path/sha256`, contract version/SHA, повний reconciliation попередніх OPEN GAP/REQ і ID receipt отримувача або очікуваний receipt.

Все файлы содержат SKU, run ID, agent ID, run mode, created_at и base package ID для delta.

Обязательные файлы:

1. `source_manifest__<sku>__<run_id>.md`;
2. `candidate_update__<sku>__<run_id>.md`;
3. `collector_handoff__<sku>__<run_id>.md`;
4. `change_events__<sku>__<run_id>.md`;
5. `package_manifest__<sku>__<run_id>.md`.

Package manifest создаётся последним и содержит SHA-256 первых четырёх файлов. Он не содержит собственный hash.

### 2A. Source/evidence delta reconciliation

Для `run_mode=source_evidence_delta` обов'язкова поштучна таблиця:

| delta_item_id | source_artifact_id | document_role | extracted_statement/asset | existing_object_ids | comparison_dimensions | delta_disposition | relation | proposed_operation | conflict_id | decision_required | rationale |
|---|---|---|---|---|---|---|---|---|---|---|---|

`document_role`: `PRODUCT_EVIDENCE|STANDARDS_OR_CREATOR_INSTRUCTION|WRONG_SKU_OR_SCOPE|UNRESOLVED_ROLE`. `delta_disposition`: `DUPLICATE_EXACT|DUPLICATE_SEMANTIC|NEW_SUPPORTING_EVIDENCE|NEW_ADDITIVE_FACT|CONFLICTING_VALUE|WRONG_SKU_OR_SCOPE|STANDARDS_OR_CREATOR_INSTRUCTION`. Comparison dimensions обов'язково містять value, unit, scope, condition, applicability, freshness і source authority. Один item не може мати кілька dispositions.

`DUPLICATE_*` має `proposed_operation=no_change`, непорожній `existing_object_ids` і не створює Change Event. `NEW_SUPPORTING_EVIDENCE` може додати evidence link, але не змінює verification status. `NEW_ADDITIVE_FACT` створює лише `PROPOSED/UNVERIFIED`. `CONFLICTING_VALUE` вимагає `conflict_id`, side-by-side comparison і `decision_required=true`; operation `update` заборонена до approved owner/Verifier decision. Standards material не стає source Паспорта і не запускає Creator.

## 4. Change Events

| event_id | Timestamp | Object type | Object/version ID | Operation | Actor type | Agent ID | Run ID | Idempotency key | Reason | Related source/evidence/gap/change |
|---|---|---|---|---|---|---|---|---|---|---|

Каждая add/update операция имеет ровно один Change Event. No_change не создаёт Change Event.

Change Event є технічним immutable журналом результату запису й не створює окремого змістовного рішення. Він посилається на `change_id`, у якого вже є `rule_provenance_ids[]` і `state_axis_record_id`. Вимога створювати власні RP/ST records для Change Event заборонена, щоб не виникав цикл `write result → state decision → Change Event → write result`.

`rule_provenance_ids[]` посилається тільки на immutable `RP-<RUN>-<NNN>` records із 06E. Відсутній ref у змістовному рішенні робить package inadmissible, але не створює нового Run status. Evidence rows, source manifests та суто технічні checks не потребують RP record, доки самі не формують змістовну класифікацію або рішення.

`state_axis_record_id` посилається на immutable `ST-<RUN>-<NNN>` із тим самим subject snapshot. Один глобальний state block не замінює subject-bound records. Відсутній, stale або прив'язаний до іншого subject record робить package inadmissible без створення нового Run status.

Виправлення відсутніх або невідповідних `RP/ST/axis_source_refs` виконується як нова редакція того самого незапечатаного пакета без нового RUN, нового питання чи повторного web research. Дозволена одна автоматична спроба корекції; повторне неспівпадіння зупиняє автоматизацію й створює діагностичний запит власнику контракту без `BLOCKED`, якщо немає окремої чинної зовнішньої перешкоди за 06E.

Для кожного змістовного рядка handoff окремо передаються `execution_status`, `evidence_status`, `contract_status` і `product_truth_decision`; точна семантика та dependency codes визначені тільки в 06E. Empty evidence не кодується нулем, а success envelope без measurements не створює evidence record.

Passport write зберігає стабільні `evidence_id`, `source_artifact_id`, `approved_claim_ref` за наявності та downstream trace refs за наявності. Runtime logs, повний manifest і tool response envelope до Паспорта не записуються.

## 9. Условия admissibility

Пакет admissible for audit, если:

- нормативный baseline валиден;
- exact SKU установлен;
- base package валиден для delta;
- все input IDs имеют coverage status;
- coverage matrix существует;
- в handoff есть сверка исходного задания и ранее открытых candidate fact/conflict/gap IDs того же SKU с текущим пакетом; для каждого элемента указаны current ID, обоснованный `out_of_scope` с решением владельца либо open gap ID; нет молчаливо исчезнувших элементов;
- все referenced IDs разрешаются;
- duplicate/collision check пройден;
- status decision table соблюдена;
- locator validation отражена;
- Change Event reconciliation пройден;
- текущая версия единого Паспорта создана первоначально в `NOT_READY` либо последующее изменение подтверждено `APPROVED candidate_update` и Change Events; passport ID/version/path/SHA совпадают с manifest;
- `PF-STATE-RECONCILIATION=PASS`: прежние OPEN GAP/REQ имеют актуальное основание или явный переход состояния; утверждённый профиль и полученные ответы учтены;
- все пять файлов существуют;
- package manifest содержит корректные hashes первых четырёх файлов.

Наличие factual/evidence gaps не запрещает аудит, если они полны и видимы. Blocking integrity failure запрещает admissibility, но не создание диагностического пакета.


## 10. Финальное дополнение контракта после повторного ревью

Этот раздел имеет приоритет над более общими формулировками выше.

### 10.1. Logical deduplication

Каждый source, evidence и evidence link содержит устойчивый deduplication key по правилам системного промпта. Run ID не входит в логическую идентичность объекта.

### 10.2. Object inventory

| object_type | object_id | base_status | current_operation | current_reference |
|---|---|---|---|---|

PASS reconciliation требует поштучного ID-level соответствия.

### 10.3. Locator validation evidence

Evidence дополнительно содержит validation_timestamp, validated_asset_hash и fragment_match_result. Validated означает повторное открытие зафиксированной версии и совпадение locator, fragment и context.

### 10.4. Self-check evidence

Каждый check содержит result PASS/FAIL/not_accessed, checked IDs, method, expected value, actual value, exceptions и reconciliation artifact либо полный перечень проверенных links.

### 10.5. Finalization order

Handoff хранит preliminary_admissibility. Окончательный package_admissible_for_audit вычисляется и записывается только в package manifest, созданный последним. После manifest первые четыре файла не изменяются. Аудитор пересчитывает их hashes.

### 10.6. Coverage status

Package manifest содержит audit_scope full_passport или limited_extraction_audit и coverage_baseline_status. Full_passport допустим только при validated_against_category_profile.
### 10.7. Historical deduplication evidence

Package manifest фиксирует checked registries/manifests, их exact paths и hashes, все lookup keys, matched object IDs и created/reused decision. Недоступный historical scope даёт FAIL и system_capability_gap.

### 10.8. Scope state basis

Каждый fact proposal и gap содержит для каждого scope dimension state и scope_state_basis. Для specified и not_applicable basis обязан ссылаться на evidence/source ID или точную нормативную норму. Без основания используется unknown и scope_gap.

## 12. Обязательное уточнение мультимедийного контракта

- Provenance включает `brand_claim`, `author_statement`, `observed_on_screen`, `measured_by_author`, `subjective_author_assessment`, `user_comment`.
- Кожний multimedia evidence, comment signal і observation містить source_id, locator та timestamp/frame_id/comment_locator.
- Claim и evidence — разные сущности many-to-many через evidence_link.
- Insight signal містить source refs, supporting/contradicting mentions, evidence status і applicability; statistics/denominator є необов’язковою method diagnostics.
- Comparison signal хранит exact_competitor_sku, same_use_scenario, same_metric, comparable_conditions, evidence обеих сторон и comparability status/gap.
- Observation зберігає довідковий `rights_information.status=KNOWN|PARTIAL|UNKNOWN|NOT_APPLICABLE`; creative approval залишається зовнішнім.
- Coverage, якщо обчислюється, зберігає numerator, denominator, unit, calculation rule і unresolved gap IDs; невідомий denominator не блокує signal.
- Acceptance checks MM-01..MM-07 перевіряють traceability, claim/evidence separation, comparison basis, signal boundary та відсутність creative fields у Паспорті.

## 13. Приёмочный контракт после аудита RUN-004

### 13.1. Evidence artifact manifest

Для каждого физического или внешнего мультимедийного производного обязательна запись:

Сводные счётчики во всех семи обязательных файлах генерируются из одного атомарного inventory. Package manifest создаётся последним. Критический FAIL устанавливает package_admissible_for_audit=false.

### 13.7. Time semantics

Change Event содержит recorded_at, occurred_at (unknown допустимо), sequence_no и не использует синтетическое время как фактическое.

## 14. Уточнение после независимого аудита RUN-005

Этот раздел устраняет неоднозначности, обнаруженные в RUN-005, и имеет приоритет над сокращёнными схемами выше.

### 14.1. Claim boundary and target resolution

Собиратель не создаёт маркетинговые claim objects. Evidence link собирателя ссылается на один существующий `fact_id`/`fact_version_id`. Если подходящего объекта нет, ссылка не создаётся: evidence получает явный `unlinked`/gap status и связанный gap. Декларация диапазона ID не считается объектом и не удовлетворяет referential integrity.

### 14.2. Closed relation vocabulary

`Relation` допускает только `supports`, `contradicts`, `insufficient`, `unclear`. Любая уточняющая семантика хранится отдельно в `relation_context`; самодельные relation values запрещены.

### 14.3. Full evidence schema and validation depth

Полная таблица раздела 3.3 обязательна для каждой атомарной evidence-записи, включая все multimedia evidence. Неизвестное значение записывается как `unknown`, неприменимое — `not_applicable`; пустое обязательное поле запрещено. Locator resolution и content validation проверяются отдельно. Для visual content PASS обязателен independently opened exact frame/crop, его SHA-256, reviewer и validation method. Иначе status — `locator_resolved_content_not_independently_verified`, а не PASS content validation.

### 14.4. Complete multimedia observation schema

Кожна observation містить: `source_id`, `locator/timestamp/frame_id`, literal observation, exact SKU/variant applicability, target type/ID, evidence boundary, confidence, `rights_information.status` і explicit gap/unlinked status. Creative placement, quality/edit decisions, consent/license approval, privacy/brand approval, owner next action та approved asset належать зовнішньому content/asset workflow.

### 14.5. Required factual preflight

PF-03 перевіряє окремо locator resolution і visual content validation; PF-08 поштучно дозволяє evidence IDs і target IDs та валідовує relation enum; PF-09 поштучно валідовує multimedia observation schema і довідковий rights information status без readiness gate. Перевірка будується за фактичними рядками/machine-readable inventory, а не за декларацією summary.

## 16. Универсальный semantic-admissibility gate

Раздел обязателен для всех товарных категорий и всех частей Паспорта. Категорийный профиль добавляет проверки полноты полей, но не изменяет этот gate.

В `preflight_report` обязательны отдельные результаты:

1. `PF-RELATION-ENUM`: поштучная проверка всех evidence links. Разрешены только `supports`, `contradicts`, `insufficient`, `unclear`.
2. `PF-ATOMICITY`: поштучная проверка всех facts. Один fact содержит одно независимо проверяемое утверждение с единым scope, status и набором доказательств.
3. `PF-EVIDENCE-REPRODUCIBILITY`: для каждого доказового фрагмента повторно открыта точная сохранённая asset version; зафиксированы SHA-256, locator, expected fragment/context и actual match. Невоспроизводимый фрагмент не может иметь relation `supports`.
4. `PF-HANDOFF-COMPLETENESS`: присутствуют и согласованы с inventory все обязательные секции, включая `first_value_projection`, `review_queue_summary`, `progress_projection`.
5. `PF-ADMISSIBILITY-COMPUTATION`: итоговая admissibility вычислена из полного набора обязательных checks.

Каждый результат содержит `check_id`, `result`, `expected`, `actual`, `method`, `checked_object_ids` либо ссылку на полный reconciliation artifact, `exceptions` и `related_gap_ids`.

Следующие условия являются Blocking FAIL:

- значение enum вне закрытого справочника;
- неатомарный fact;
- `supports` для невоспроизводимого fragment/locator/context;
- отсутствие обязательной секции или проекции;
- missing check либо неполное покрытие применимых объектов;
- положительная admissibility при любом Blocking FAIL.

Counts, hashes, наличие файлов и referential resolution проверяются отдельно и не компенсируют semantic FAIL. При Blocking FAIL пакет может быть создан только как диагностический с `package_admissible_for_audit=false`.

## 17. Delta/event и coverage closure gate

В `preflight_report` обязательны три дополнительные проверки:

### 17.1. PF-DELTA-EVENT-RECONCILIATION

Для каждого объекта текущей редакции фиксируются base hash/value, current hash/value, ожидаемая и фактическая `Operation`, Change Event ID. Любое изменение relation, status, locator, scope или payload требует `update`. Каждый `add/update` имеет ровно одно событие текущей редакции; `no_change` не имеет нового события.

### 17.2. PF-SUPPORTS-MATCH-CONSISTENCY

Каждый evidence link із `Relation=supports` обязан ссылаться на evidence с воспроизводимыми exact fragment, context и locator в точной asset SHA-версии. `fragment_match_result`, locator validation и relation не могут противоречить друг другу. При отсутствии воспроизводимого match допустимы только `insufficient` или `unclear` и открытый gap, если он нужен.

### 17.3. PF-COVERAGE-INVENTORY-CLOSURE

После любого split, merge, add или update fact единый current inventory заново проецируется в coverage matrix, review queue и progress projection. Каждый current fact ID получает явный coverage disposition. Диапазон или старый ID не покрывает новые atomic IDs без их явного перечисления или машиночитаемого membership.

Несовпадение Operation/events, `supports` без match или отсутствующий current fact ID являются Blocking FAIL для `package_admissible_for_audit`.

## 18. Full-matrix і exact-schema gate

### 18.1. PF-COVERAGE-FULL-MATRIX

Validator обнаруживает все coverage rows из фактического payload, включая строки вне ожидаемого диапазона. Для каждого current fact ID вычисляется полный список memberships. PASS требует ровно одного канонического membership/disposition. Повторное упоминание может существовать только с явным `reference_only=true` и не входит в numerator, denominator или coverage counts. Непроверенная строка, duplicate membership или missing fact ID дают FAIL.

### 18.2. PF-HANDOFF-SCHEMA-EXACT

Validator сравнивает actual fields каждой обязательной handoff-секции и каждого row с актуальной схемой контракта. Для `review_queue_summary` обязательны: `work_item_id`, `referenced_object_type`, `referenced_object_id`, `priority_rank`, `required_decision_or_action`, `significance`, `evidence_ids`, `blocking_gap_ids`, `next_safe_action`, `owner_role`, `acceptance_criteria`.

Аналогичная exact-field проверка применяется к `first_value_projection`, `progress_projection` и другим обязательным секциям. Наличие heading, неполной таблицы или aggregate count не заменяет row-level schema validation. Любое отсутствующее required field является FAIL и блокирует положительную admissibility.

## 18.3. PF-EXTENSION-FIELD-RECONCILIATION

Категорийний профіль є baseline обов’язкових полів, а не закритим переліком фактів. Кожен факт, який не має точного семантичного відповідника, повинен бути присутнім у Паспорті як `extension_field`, а не бути відкинутим або записаним у приблизне поле. Для кожного розширення обов’язкові: унікальний `extension_id`, `source_label`, `normalized_label` (або `null`), `value`, `unit` (або `not_applicable`), `scope`, `source_artifact_id`, точний locator, evidence/verification status і `extension_reason` (`NO_CANONICAL_FIELD`, `CATEGORY_SPECIFIC` або `SOURCE_ADDITIONAL`).

`PF-EXTENSION-FIELD-RECONCILIATION` перевіряє, що кожен extension має рівно один disposition (`accepted_extension`, `mapping_pending_review` або `rejected_with_reason`), не дублює канонічне поле без пояснення і не змінює затверджений profile baseline. Відсутній extension metadata, мовчазна втрата факту або примусове маппування в чуже поле — Blocking FAIL. `MAPPING_PENDING_REVIEW` зберігає факт у Паспорті, але не робить його Product Truth і не додає до обов’язкової схеми профілю.

## Контроль размещения, полноты и версий источников (22.09.2026)

До начала run установи точный `sku_id` только по значению возле явного поля/подписи `SKU` в предоставленном документе. Значение может содержать цифры, буквы или их сочетание и сохраняется дословно, включая начальные нули, дефисы и регистр. Модель, название товара, другое поле, код комплекта, имя файла или папки не являются заменой SKU. Если явного `SKU` нет, значение не читается или найдено несколько конфликтующих значений, запроси точный SKU у пользователя и не создавай `run_id`, Паспорт или `product_root` до ответа. Затем зафиксируй абсолютный `product_root`, имя которого точно совпадает с подтверждённым `sku_id`; версию/модель товара храни отдельно. Все файлы, созданные или загруженные для этого товара, включая временные извлечения, кадры, контактные листы, скрипты обработки и previews, размещай внутри `product_root`. Общие инструменты могут храниться вне папки товара; продуктовые входы и результаты в их каталогах не оставляй. Внешний временный файл допускается только на время операции: после копирования внутрь папки товара проверь SHA-256 и удали временную копию. При невозможности удалить зафиксируй blocker с точным путём.

В `артефакти/YYYY-MM-DD/` храни неизменные файлы по дате локальной записи. В реестре для каждого файла укажи `artifact_id`, роль (`SOURCE_ORIGINAL`, `DERIVED_EVIDENCE`, `DIAGNOSTIC_RESPONSE`), исходный URL/файл, время записи, версию, SHA-256, `ACTIVE/OLD` и `parent_artifact_id` для производного. Пустой или неудачный ответ не считай содержательным источником. Для двух захватов одного URL укажи `replaces`, `parallel_snapshot` либо `duplicate_of` с основанием. При замене переведи предыдущую запись в `OLD` и сохрани оба файла; одинаковый SHA-256 не образует новую редакцию содержания.

Перед `package_admissible_for_audit=true` перечисли все ссылки из входных документов и сопоставь каждой статус `PROCESSED`, `FAILED_WITH_ATTEMPTS` либо `OWNER_EXCLUDED`. Для каждого отказа укажи конкретные попытки и результат. Доступное связанное видео, папку или документ нельзя объявлять необязательным через `limited_extraction_audit`. Перед `no_match` в HTML проверяй raw text и декодированные embedded JSON/escaped fields с точным locator. Проверь отсутствие продуктовых файлов вне `product_root`; нарушение даёт `BLOCKED` до исправления. Старый sealed package не редактируй: выпускай новую редакцию и повторяй manifest/hash check.

Перед handoff Собиратель запускает read-only контроли из `tools/README.md`: `passport_package_check.js` и `handoff_integrity_check.js`. Для второго контроля в handoff явно указываются абсолютный путь к текущему manifest и либо `--base-manifest none` для первого RUN, либо абсолютный путь к manifest прямого предыдущего пакета. Результат инструмента классифицируется по 00A: подтверждённый прямым read-back содержательный defect из действующего gate запрещает `package_admissible_for_audit=true`; ошибка парсера, unsupported format и только manifest/parent/checksum mismatch являются `DIAGNOSTIC_METADATA_MISMATCH` и сами по себе передачу не запрещают. Инструмент не вправе создавать новый blocker code. Sealed revision не редактируется; если прямой read-back подтвердил реальный дефект, выпускается новая immutable revision.
## Контроль отрицания и направления порога (23.09.2026)

Для каждого количественного порога извлекай полную смысловую фразу, включая отрицание, сравнительный оператор, число, единицу, объект и условие. Проверяй переносы строк, разрывы слов и соседние строки PDF/HTML: `не больше`, `не меньше`, `до`, `от`, `максимум`, `минимум` нельзя отрезать от числа. Нормализуй оператор отдельно (`<=`, `>=`, `<`, `>`, `=`) и сохраняй исходный fragment без потери слов. `fragment_match_result=MATCH` означает совпадение текста, но сам по себе не доказывает совпадение смысла.

Перед sealed manifest выполняй `PF-NEGATION-COMPARATOR`: для каждого затронутого fact/evidence/link ID сопоставь оператор источника, оператор нормализованного факта, единицу и scope; сохрани исходную фразу и результат. Любое несовпадение или неразрешённый перенос даёт Blocking FAIL, а relation=`supports` не допускается. При исправлении старого объекта создай новую версию пакета с delta `update` и Change Event; старый sealed пакет не меняй.
## Gate единого Паспорта и допустимых выходов (23.09.2026)

## Gate полноты source discovery и структуры (24.09.2026)

Пакет содержит `knowledge_coverage_matrix` со схемой `source_or_query_id, locator, source_class, access_attempt_ids, acquired_artifact_ids, extracted_object_ids, disposition, residual_gap_ids`. Все embedded links входных файлов входят в denominator. Дополнительный public search по exact SKU/версии фиксирует query, checked source classes, capture date и disposition; остановка допустима после покрытия priority classes и отсутствия net-new объектов в двух последовательных независимых source classes.

`PROCESSED` валиден только при наличии acquired artifact или reproducible inventory, content extraction и disposition к конкретным facts/evidence/conflicts/gaps/relations/opportunities. URL-only row, заголов, thumbnail или diagnostic response не дают `PROCESSED`. Недоступная ссылка получает `FAILED_WITH_ATTEMPTS` только с timestamped attempt log; `OWNER_EXCLUDED` — только с owner decision reference. Нарушение даёт `PF-LINK-RECONCILIATION=FAIL`, `PF-KNOWLEDGE-COVERAGE=FAIL` и `package_admissible_for_audit=false`.

`passport_section_matrix` перечисляет все required sections утверждённой структуры и их статус `PRESENT_WITH_DATA | PRESENT_MISSING_WITH_GAP`. Отсутствующий обязательный раздел даёт `PF-PASSPORT-SECTION-COMPLETENESS=FAIL`. JBTD/Buyer Episodes хранятся только как read-only relation/proposal/gap; observed use context не подменяет accepted JBTD.

## PF-PASSPORT-SOURCE-LINK-COMPLETENESS (24.09.2026)

В едином Паспорте раздел `Джерела і походження` содержит по одной строке на каждый source/link из source manifest и `knowledge_coverage_matrix`. Обязательные поля: `source_id`, `source_title`, `source_type`, `original_url_or_file_locator`, `canonical_or_stable_url`, `local_artifact_path`, `access_status`, `captured_at`, `last_checked_at`, `gap_or_attempt_log_id`. Отсутствующее значение явно `not_applicable` с reason; пустое поле запрещено.

Для DOCX каждый web source имеет настоящий hyperlink relationship с полным safe target. Проверка извлекает OOXML relationships, а не только ищет текст `http`. Signed/tokenized secrets не публикуются: используй stable safe URL и архивный artifact.

## 20. `passport_restore_candidate`

Для `run_mode=passport_restore` вихід містить: new Passport ID/version/state/path/SHA; `restored_from_passport_id/version/archive_manifest_sha256`; shared lineage ID; current active Passport snapshot; staging/canonical target paths; imported value/evidence counts; reset verification count; read-back results; unresolved conflicts; `ready_for_atomic_switch=true|false`; rollback locator. - target canonical path;
- identity, path-containment, source-registry і read-back results;
- unresolved gaps/conflicts;
- `ready_for_atomic_switch=true|false`;
- rejection codes;
- rollback/quarantine locator;
- handoff only to Coordinator.
